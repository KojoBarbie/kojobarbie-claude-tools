# スクリーンショット1枚をどう読むか

カードの品質がこの vault の価値を決める。目的は**模写できるようにすること**ではなく、
**別のアプリに移植できる原理に翻訳すること**。

## 手順（1枚あたり）

### 1. 0.5秒テスト

画像を見て、最初に目に入った要素を1つだけ挙げる。それが設計者の意図した主役かを判定する。
ここがズレているスクショは、それ自体が学び（`verdict: mixed` か `anti`）。

### 2. 何の瞬間かを言う

画面名ではなく**ユーザーの状態**で言う。
「ホーム画面」ではなく「初回起動でまだデータが0件の状態」「3日サボった後に開いた瞬間」。
デザインの良し悪しは常に「どの瞬間に対して良いか」でしか判定できない。

### 3. なぜ効くかを、効く条件とセットで書く

ここが本番。**「効く条件」を書かないカードは書かなかったのと同じ**。
条件抜きの「余白が広くて上品」は、賑やかであるべきアプリに機械的に適用されて事故る。

- ❌「余白が広くて洗練されている」
- ⭕「1画面に1操作しかないので余白で埋めても情報が足りる。*効く条件*: 操作が単一の画面。
  リスト画面に同じ余白を使うと1画面3件しか出ず、走査性が落ちる」

### 4. 数値に落とす

目測でよいので比率で読む。絶対値より**比**が移植可能。

- 余白: 画面端 / カード内 / セクション間 の3つ。8の倍数に乗っているか
- 角丸: 要素種別ごとの半径。揃っているか階層になっているか
- タイポ: 主役と脇役の**サイズ比**（例: 数字48 : ラベル13 ≒ 3.7倍）
- 強調装置: 何がどう光っているか。1画面に何回出ているか
- パレット: スポイト的に主要4〜6色。「この色は何に使う色か」を言えるか

### 5. 静止画から読めないものは推測と明記する

モーション・触覚・音は写らない。推測を書くのは構わないが `（推測）` を付ける。
**動きの推測は特に価値が高い**ので、省略せず書く（例:「この紙吹雪は0.5秒程度と推測。
毎日使う画面なので長いと邪魔になるはず」）。

### 6. アンチも同じ熱量で書く

競合アプリの雑な画面は `verdict: anti` で必ず保存する。
「既存アプリの体験が雑」は新規アプリの勝ち筋そのもので、後で証拠として引ける。
何が雑かを「なぜユーザーが困るか」で書く（「ダサい」では使えない）。

## 書いてはいけないこと

| ❌ | なぜダメか |
|---|---|
| 「洗練されている」「モダン」「おしゃれ」 | 再現できない。次に何をすればいいか分からない |
| 「Appleらしい」「Material Design準拠」 | 出典の名前であって設計判断ではない |
| 効く条件を書かない | 別ジャンルに機械的にコピーされて事故る |
| 全部を褒める | 5個の指摘より1個の「これが効いている」の方が使える |
| 画面の要素を上から順に説明する | スクショを見れば分かる。書くのは**見えないもの**（意図と条件）だけ |

## アプリ名が分からないとき

メタJSON の `message_text`（Slack に添えたコメント）を最優先で見る。
それでも不明なら、画面内のロゴ・独自UIから推定し、`app: 不明（推定: XXX）` と書く。
**アプリ名が不明でもカードは作る** — 名前より、そこにある設計判断のほうが資産になる。

## 1回の取り込みで何枚まで見るか

inbox に大量に溜まっていても、**1回の実行で分析するのは20枚まで**。
残りは inbox に置いたまま次回に回す（メタJSON の `analyzed` が false のものが対象）。
雑に流し込んだ50枚のカードより、丁寧な10枚のほうがパターン集約に効く。
