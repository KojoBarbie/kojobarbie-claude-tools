# design-vault の構造仕様

置き場所は `$PRD_VAULT_DIR/design-vault/`（デフォルト `~/dev/prd-vault/design-vault/`）。
prd-vault は private なので他社アプリのスクリーンショットを置いてよく、
かつ `showcase/` と同一リポジトリなので **showcase のページから参照画像をそのまま表示できる**。

```
design-vault/
├── README.md            # 人間向けの使い方（チャンネル名・運用ルール）
├── inbox/               # 収集直後の未分析画像 + メタJSON。分析が済んだら空になる
├── refs/{app-slug}/     # 分析済み画像の本体（長辺1200pxのJPEG）
├── cards/{id}.md        # 画像1枚 = カード1枚
├── patterns/{name}.md   # カードを横断して帰納したパターン集 ← 本体価値はここ
├── index.json           # カードの機械可読インデックス（検索用）
└── .slack_state.json    # 収集スクリプトの取り込み位置（触らない）
```

## カード（`cards/{id}.md`）

`{id}` は収集スクリプトが付けた `YYYYMMDD-{SlackFileID}`。1枚1ファイルで、frontmatter と本文を持つ。

```markdown
---
id: 20260808-F09ABCDEF
app: Duolingo
app_slug: duolingo
platform: ios
screen: completion        # 下の「screen の語彙」から選ぶ
category: 学習
mood: [祝祭的, ゲーム的, 明るい]
palette: ["#58CC02", "#FFFFFF", "#1CB0F6", "#4B4B4B"]
techniques:
  - 成果を特大の数字ひとつで見せる
  - 完了を紙吹雪とサウンドで祝う
verdict: strong           # strong | mixed | anti
image: refs/duolingo/20260808-F09ABCDEF.jpg
collected_at: 2026-08-08
---

## 何の画面か
1レッスン完了直後のサマリ画面。獲得XP・連続日数・正答率を見せて次のレッスンへ送る。

## 効いている理由（再利用できる形で）
1. **成果を1つの特大数字に集約している** — 3つの指標があるのに、視線は「+15 XP」に一直線。
   複数の実績を同格で並べると何も残らないが、1つを主役にすると「進んだ」という感情が残る。
   *効く条件*: 1セッションで区切りが付く体験（学習・運動・タイマー）。連続的な記録アプリでは弱い。
2. **祝いが0.6秒で終わる** — 紙吹雪は短く、次アクションのボタンがすぐ触れる。
   祝う演出は長いほど2回目以降ノイズになる。
   *効く条件*: 毎日繰り返す体験ほど演出は短くする。

## 数値で読める設計
- 余白: カード内 24 / セクション間 32（8の倍数）
- 角丸: カード 16、ボタン 全丸（pill）
- タイポ階層: 数字 48/Bold → ラベル 13/Medium/大文字 → 本文 15/Regular
- 強調装置: 塗りつぶしの緑 pill ボタン（1画面1つ）

## 使いどころ
「1回やったら区切りが付く」アプリの完了画面。
記録が積み上がるだけで完了の概念がないアプリに移植すると、祝う対象が無く空回りする。
```

### `screen` の語彙（固定。増やすときはこの表を更新する）

`first-run` / `onboarding` / `home` / `list` / `detail` / `input` / `empty` /
`loading` / `completion` / `paywall` / `settings` / `stats` / `error` / `store`（App Store掲載画像）

### `verdict` の使い分け

- `strong` — 真似する価値のある設計
- `mixed` — 一部だけ良い（例: レイアウトは秀逸だがコピーが煽り）。良い部分と悪い部分を両方書く
- `anti` — **アンチパターンとして保存する**。競合アプリの雑な体験はこれで貯める。
  「既存アプリの体験が雑だからUXで勝てる」という判断の証拠になるので、strong と同じくらい価値がある

## index.json

カード全件の機械可読インデックス。カードを追加/更新したら必ず同時に更新する。

```json
[
  {
    "id": "20260808-F09ABCDEF",
    "app": "Duolingo",
    "screen": "completion",
    "category": "学習",
    "mood": ["祝祭的", "ゲーム的", "明るい"],
    "verdict": "strong",
    "techniques": ["成果を特大の数字ひとつで見せる", "完了を紙吹雪とサウンドで祝う"],
    "image": "refs/duolingo/20260808-F09ABCDEF.jpg",
    "card": "cards/20260808-F09ABCDEF.md"
  }
]
```

## パターン（`patterns/{name}.md`）

**このリポジトリの本体価値**。カード単体は「1つの実例」でしかないが、
同じ `screen` のカードが5枚以上溜まったら横断して帰納し、「型」に落とす。
nemuiasa 1件からの演繹を、N件からの帰納で置き換えるのがこの仕組みの目的。

```markdown
---
pattern: completion-moment
title: 完了の瞬間をどう祝うか
lens: 9                    # app-design-craft の対応レンズ番号
examples: [20260808-F09ABCDEF, 20260810-F09XXXXX, ...]
sample_size: 12
updated: 2026-08-08
---

## この型が解いている問題
（ユーザーのどんな感情/行動の問題を解いているか。1〜2文）

## 12例から見えたこと
- 12例中9例が「成果を1つの数字に集約」していた
- 演出時間は0.4〜0.8秒に集中。1秒超は3例だけで、いずれも週次サマリなど頻度の低い画面だった
- …（必ず「何例中何例」で書く。印象で書かない）

## 型
### A. 数字ひとつ型（9/12）
- **使う条件**: 1セッションで区切りが付く体験
- **実例**: [[20260808-F09ABCDEF]]（Duolingo）
- **実装の勘所**: 数字は44pt以上、ラベルは数字の1/3以下

### B. 積み上げ可視化型（2/12）
…

## やってはいけない
- （アンチ例を `verdict: anti` のカードから引く）

## 効かない場面
（この型が空回りするアプリの条件。ここを書かないと辞書化して誤用される）
```

### パターンを作る/更新するタイミング

- 同一 `screen` のカードが **5枚**溜まったら新規作成
- 既存パターンの `sample_size` から **+5枚**増えたら更新（結論が変わったかを必ず検証する）
- カードを足しただけでパターンを更新しないのは、この vault を単なる画像置き場に劣化させる最大の失敗
