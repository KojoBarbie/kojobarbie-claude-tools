# App Idea Hunt

海外市場のトレンドから「日本の個人開発者が1〜2週間で作れて、確実に収益が上がる」アプリのネタを発掘し、PRD（要件定義書）として `prd-vault` にPR提出するまでを自動で行う。

**このパイプラインの成果物はPRD 1本のPR（トンマナ＋モックの showcase ページ込み）とSlack通知**。ユーザーはPRをマージ（=Go）またはクローズ（=ボツ）するだけでよい。その体験を壊さないよう、途中でユーザーへの質問はせず、判断はこのスキルの基準に従って自分で下す（例外は指名モードの停止条件だけ — そこでも同期的に聞くのではなく issue にコメントを残して終了する）。

## 起動モード

最初にどのモードで呼ばれたかを判定する。どのモードでも Step 0（準備）は必ず通り、成果物の形（PRD の PR + Slack 通知）は同じ。

| モード | 起動条件 | 通す Step |
|---|---|---|
| **hunt**（既定） | 週次の自動実行、「ネタを探して」など対象が指定されていない依頼 | Step 0 〜 11（全部） |
| **nominate**（指名） | prd-vault に `idea` ラベルの open issue がある、または「`ideas/○○` を PRD にして」「このアイデアを回して」と特定のネタを指定された | Step 0 → Step 2 → Step 4 〜 11（Step 1 の発散だけスキップ）。詳細は末尾の[指名モード](#指名モードidea-ラベルの-issue--手元のアイデア) |
| **revise**（改訂） | prd-vault のオープンPRにユーザーのコメントが付いている | 末尾の[改訂モード](#改訂モードprコメントへの対応) |

## 前提

**最初に `~/.config/app-factory/config.env` を読み込む**（`[ -f ~/.config/app-factory/config.env ] && . ~/.config/app-factory/config.env`。無ければ各変数は括弧内のデフォルト値を使う）。

| リソース | パス |
|---|---|
| PRDリポジトリ | `$PRD_VAULT_DIR`（デフォルト: `~/dev/prd-vault`。GitHub: `$GITHUB_OWNER/$(basename "$PRD_VAULT_DIR")`、デフォルトブランチ `main`） |
| 設定 | prd-vault 内の `config.yml` — 本数・スコア重み・注目カテゴリ・除外条件。**毎回最初に読む** |
| PRDテンプレート | prd-vault 内の `templates/PRD_TEMPLATE.md` |
| Slack webhook | `SLACK_WEBHOOK_URL_PRD`（`$APP_FACTORY_HOME/.env`（デフォルト: `~/dev/others/claude-cron/.env`）を `set -a && source && set +a` で読み込む） |
| Slack投稿スクリプト | `python3 $APP_FACTORY_HOME/.claude/skills/slack-post/scripts/slack_post.py --file <md> --header <題> --webhook-url "$SLACK_WEBHOOK_URL_PRD"`（`slack-post` スキルは作者環境の前提。無い環境では curl で webhook に直接 POST する） |
| 競合チェック | `bash {skill_dir}/scripts/jp_appstore_search.sh "検索語" [limit] [country]` |

## Step 0: 準備

1. `cd "$PRD_VAULT_DIR" && git checkout main && git pull`
2. `config.yml` を読み、本数・重み・注目カテゴリ・除外条件を把握する
3. **重複回避リスト**を作る: `prd/` `ideas/` `rejected/` の全ファイル名と各ファイル冒頭の概要、および `gh pr list --state all --limit 50` のPRタイトルを確認。過去に提案・却下したものと同じネタを再提案しない（`rejected/` は却下理由も読む — ユーザーの好みの学習データとして最重要）
   - **指名モードでは、指名された候補自身は重複回避の対象にしない**（`ideas/` にあるものを昇格させるのが目的なので、「既にある」を理由に弾いてはいけない）。ただし `rejected/` に同じネタがあった場合は却下理由を読み、指名モードの停止条件に従って判断を仰ぐ

## Step 1: リサーチ（発散）

海外市場から候補を **10〜20個** 集める。1つの情報源に頼ると偏るので、必ず複数の切り口を使う。具体的な情報源と手順は [references/research-sources.md](references/research-sources.md) を読むこと。

`config.yml` の注目カテゴリ（課金されやすい=「課金した先に得られる未来」が想像しやすいカテゴリ）を重点的に探す。ただし発散フェーズなのでカテゴリ外の有望株を捨てる必要はない — 加点で差が付くだけ。

集める情報: アプリ名 / 国・ソース / カテゴリ / 何が受けているか / 収益モデル / 規模感。

`$APP_FACTORY_HOME` 内で実行されている場合は `/overseas-app-trends` スキル（Apptopia・Google Trends等の取得手順）も活用できる（作者環境にあるスキルの前提。無い環境ではスキップしてよい）。

## Step 2: 除外フィルタ

`config.yml` の `exclusions` を各候補に適用する。特に:

- **ネットワーク効果前提（SNS・マッチング・コミュニティ等）は即除外**。ユーザーが集まらないと価値が出ないアプリは、集客リソースのない個人開発者が最も失敗しやすい類型
  - **例外**: カップル向け・家族向けなど「既にいる特定の相手を1人招待すれば価値が成立する」クローズドアプリはネットワーク効果に当たらないので除外しない（2人だけの閉鎖型SNS等）。不特定多数を集めるマッチングは引き続き除外
- **ゲームは全ジャンル除外**
- **マネタイズが描けないものは除外**。「便利だが誰も金を払わない」アプリは作らない
- 1〜2週間のMVPに収まらない規模、サーバー費が収益を食う構成、医療診断・金融助言など審査/法規制リスクが高いものも除外

除外した候補のうち「惜しかったもの」は理由とともにメモしておく（Step 9 で `rejected/` に記録する）。

## Step 3: 日本展開への翻案

生き残った候補それぞれについて「日本の個人開発者として出すならどうなるか」を1〜3行で構想する。単なる翻訳コピーではなく、日本の文脈（習慣・季節・制度・既存アプリの不満）に合わせた角度を付ける。ここで魅力が出ないものは脱落させてよい。

## Step 4: 競合チェック（日本App Store）

各候補について、想定される検索語 **2〜3語**（日本語・英語両方）で調査する:

```bash
bash {skill_dir}/scripts/jp_appstore_search.sh "睡眠 記録" 10 jp
```

判定基準:
- **強い競合がいる**（評価件数1万超のアプリが同じコア価値を無料で提供、かつ最終更新が1年以内）→ 脱落。`rejected/` 行きにし、競合名を理由に書く
- **弱い競合のみ**（評価が少ない、更新停止、UXが古い、日本語対応が雑）→ 通過。競合の「隙」をPRDの差別化欄に使う
- **競合ゼロ** → 通過だが「なぜ誰もやっていないのか」を一度疑う（需要がない可能性・技術/審査上の壁）。理由に納得できたら通過

## Step 5: スコアリングと選定

通過候補を `config.yml` の `scoring` の重みで100点満点採点し、表にまとめる。上位 `prds_per_run` 本をPRD化し、次点 `ideas_to_stock` 本を `ideas/` にストックする。

**指名モードでは相対比較が成立しない**（候補が1件なので必ず1位になる）。上位N本を選ぶ代わりに、`config.yml` の `pipeline.nomination_min_score`（デフォルト60）を通過ラインとした絶対判定に切り替える。未達なら PRD 化せず、点数の内訳と弱点を添えて判断を仰ぐ（指名モードの停止条件を参照）。

採点で迷ったら「**月5万円ポートフォリオへの寄与が最も確実なもの**」を優先する。派手さより、支払い意欲が実証済み（参考元が有料で売れている）であることを重視する。

monetization の採点では「**課金した先に得られる未来**」が一言で言えるかを必ず確認する（例: 英語が話せるようになる / 痩せる / 仕事の工数が減る / お金の不安が減る）。使った瞬間は便利でも未来の変化が見えないアプリは課金されにくいので、言えないものは monetization を辛めに付ける。

## Step 6: ジョブ分析（PRD化の関門）

スコアリングで選ばれた候補を、PRDに落とす前に**ジョブ理論で分析**する。分析に耐えない候補はスコアが高くてもここで落とす（`ideas/` に理由付きで残す）。

1. **ジョブ分解**: 元ネタのサービスを「機能的/感情的/社会的ジョブ」と「誰が・どんな状況で・何の代わりに雇うか」に分解する。代替品は同カテゴリアプリに限定しない（紙・我慢・人への依頼を含める）
2. **人気の因果仮説**: なぜ海外で人気/急上昇なのかを、(a) ジョブ自体が新しく生まれた、(b) 既存ジョブの解決コストを下げた、(c) マーケが上手いだけ、のどれかに分類し根拠を示す。(c) しか説明が立たない候補は原則落とす。急上昇ネタはきっかけ（バイラル・特集・季節性）と再現可能性を必ず評価する
3. **日本への移転可能性**: 同じ状況・同じジョブが日本に存在するか、既に支配的な代替解決手段がないか、サービス側で調整が必要な点は何かを検証する。ジョブが日本に存在しない/別の解決が支配的なら落とす
4. **KPI 設計**: コア行動を1つ定義し、収益に至る KPI ツリー・計測イベント一覧・マイルストーン（M1〜M3）・見送り基準を決める。数値目標は必ず具体化する:
   - M1〜M3 の基準値は**グローバル初期値の丸写し禁止**。カテゴリの一般的な水準・元ネタアプリの実績・想定市場規模から、このアプリ固有の数値を**根拠1行付き**で設定する
   - 収益目標は「**収益化手段 × 想定転換率 × 必要ユーザー数**」の算数を1行書く（例: 買い切り¥600 × 転換率3% × 月間DL 300 ≈ 月¥5,400）

## Step 7: PRD執筆

選ばれた候補について追加リサーチ（参考元アプリのレビュー・価格・機能詳細、必要な技術の実現性）を行い、`templates/PRD_TEMPLATE.md` の全セクションを埋める。

- ファイル名: `prd/{english-slug}.md`（例: `prd/sleep-streak.md`）
- **「ジョブ分析」「KPIと計測計画」の2セクションを必ず埋める**（Step 6 の分析結果をそのまま落とす）。セクション定義は [references/prd-sections.md](references/prd-sections.md)。prd-vault のテンプレートにこの2セクションが無ければ、この references の内容で PRD に直接書く（テンプレート自体の更新も1回だけ提案してよい）
- 全セクションを具体的に書く。「〜を検討する」のような先送りは書かない — このPRDだけを読んで開発を開始できる状態にする
- マネタイズ欄は必ず金額まで書く（価格、想定DL数、月次収益見込みの逆算）。加えて「このアプリを使い続けたらユーザーがどう変わるか」を1行で書く — 課金設計は機能を売るのではなく未来の変化を見せるのが軸。ペイウォールの訴求文言もこの1行から作る
- **課金の実装基盤は RevenueCat を既定とする**（StoreKit を直叩きしない）。買い切り・サブスクいずれでも RevenueCat の Offering／Entitlement で管理する前提で「技術メモ」に書く。理由: レシート検証・購入復元・クロスデバイス同期を肩代わりでき、後からサブスク化や価格ABテストに拡張しやすい。無料プラン（追跡月商 $2,500 まで無料）の範囲なので個人開発でも実質コストゼロ
- 「デザイン方向性メモ」は後続の `app-kickoff` がコンセプトシートを作る際の入力になるので、世界観が想像できる程度に書く（Step 8 のトンマナページとも一致させる）

## Step 8: モックとトンマナ（showcase）

PRD化する案ごとに、prd-vault の `showcase/`（Next.js App Router・静的エクスポート・Firebase Hosting デプロイ前提）へ確認用の2ページを作る。**PRDと同じブランチ・同じPRに含める**（コミットは Step 10 で行う）。`ideas/` 止まりの案には作らない。ディレクトリ構成・apps.json スキーマ・ページに含める要素・ブートストラップ手順は [references/showcase-spec.md](references/showcase-spec.md) を読むこと。

- `showcase/app/apps/{slug}/tone/page.tsx` — トンマナ: カラーパレットのスウォッチ（hex付き）・タイポグラフィ・余白/角丸の方針・ムードキーワード・Do/Don't。**ダークモード禁止**の規約に沿った明るい配色にする
- `showcase/app/apps/{slug}/mock/page.tsx` — コア画面のモック: CSSで描くiPhoneフレーム内に主要1〜2画面。トンマナページの配色に従う。静的でよい
- `showcase/apps.json` に `{ slug, name, status, prd, createdAt }` を追記する（一覧ページ `showcase/app/page.tsx` がこれを読む）
- `showcase/` が存在しなければ references の手順で最小構成をブートストラップし、Firebase Hosting 接続（1回だけの人間作業）を Step 11 の Slack 通知にチェックリストで含める
- 作成後、`showcase/` で `npx next build` が通ることを確認する（`node_modules` が無ければ先に `npm install`）

## Step 9: 記帳（main に直接コミット）

PRD本体より**先に**、ブックキーピングを main に直接コミットして push する:

- `ideas/{slug}.md` — 次点候補。3〜5行の概要＋スコア＋見送り理由
- `rejected/{slug}.md` — 除外・脱落した候補。1〜3行の概要＋却下理由（`競合あり: {アプリ名}` / `SNS系` など）

これらをPRブランチに入れると、PRが却下されたときに記帳まで消えてしまう。必ず main 側に分けること。

## Step 10: PRD のPR作成

```bash
git checkout -b prd/{slug}
git add prd/{slug}.md showcase/ && git commit -m "PRD: {アプリ名（仮）}"
git push -u origin prd/{slug}
gh pr create --title "PRD: {アプリ名（仮）} — {一言コンセプト}" --body "..."
```

PR本文の冒頭に、レビュー観点を明記する:

```
このPRのレビューで見てほしいのは「ジョブ分析」と「KPIと計測計画」です。
機能や技術ではなく、①ジョブ分解が納得できるか ②人気の因果仮説が信じられるか
③日本への移転可能性の検証が甘くないか ④KPIに具体的な目標数値と根拠が入っているか、
を判断してマージ/クローズ/コメントしてください。
マージ = M1未達なら maintain 行き、という見送り基準への合意も含みます。
```

続けて: 一言コンセプト / 総合スコアと内訳 / 想定月次収益 / 競合チェック結果の要約 / トンマナ・モックページ（showcase）の場所 / 「マージ=Go、クローズ=ボツ、コメント=修正指示」の操作ガイド、を含める。ドラフトにはしない（マージ操作が承認フローなので、マージ可能な状態で出す）。

## Step 11: Slack通知

PRD要約（アプリ名・一言コンセプト・スコア・想定収益・PRリンク・操作ガイド1行）を `/tmp/prd_notify.md` に書き、slack-post スクリプトで `$SLACK_WEBHOOK_URL_PRD` に投稿する。長文を貼らない — 読むのはスマホ。詳細はPRリンク先で読んでもらう。

トンマナ・モックの確認先も添える:

- Firebase Hosting 接続済みなら `https://{サイト名}.web.app/apps/{slug}/tone` と `.../apps/{slug}/mock` のURL
- 未接続なら「PR内のファイルで確認」と一言添え、Step 8 でブートストラップした場合は Firebase Hosting 接続のチェックリスト（prd-vault 専用の Firebase プロジェクトを作り `firebase deploy --only hosting`。1回だけの人間作業。詳細は showcase-spec.md）を含める

## 収穫ゼロのとき

全候補が基準を満たさなかった場合、無理にPRDを出さない（質の低い提案はパイプラインの信頼を毀損する）。`rejected/` への記帳だけ行い、Slackに「今週は基準を満たすネタがなかった」と主な脱落理由とともに短く報告する。

（これは hunt モードのルール。指名モードで候補が基準を満たさなかった場合は「指名モードの停止条件」に従う）

## 指名モード（`idea` ラベルの issue / 手元のアイデア）

`ideas/` に眠っている候補を昇格させたい、あるいは自分の手元にあるアイデアを同じ基準でリサーチ・採点させたいときのモード。**発掘（Step 1 の発散）をスキップする機能であって、審査を省略する機能ではない**。

### 入力の受け取り

```bash
gh issue list --repo "$GITHUB_OWNER/$(basename "$PRD_VAULT_DIR")" --label idea --state open \
  --json number,title,body,labels,comments
```

処理対象は「`processed` ラベルが無く、かつ（コメントが無い or 最終コメントが `🤖` で始まらない）」もの。最終コメントが `🤖` のものは判断待ちなのでスキップする。会話から指名された場合は issue 番号が無いだけで、以降の手順は同じ。

入力は2種類:

- **昇格** — `ideas/{slug}.md` が存在する場合。そのファイルを候補記述として使う（概要・スコア・見送り理由が既に書かれている）。**見送り理由が解消されているかを必ず再評価する**（例: 「hirune が一段落してから」なら `portfolio.yml` で hirune の現ステージを確認し、解消されていなければ停止条件として扱う）
- **持ち込み** — 対応する `ideas/` が無い場合。issue 本文／ユーザーの説明をそのまま候補記述として使う。参考元アプリや収益モデルが書かれていなければ、**その候補についてだけ** [references/research-sources.md](references/research-sources.md) の情報源で裏取りする（類似の海外アプリ・価格・実績を探す。10〜20個集める発散はしない）

### 通す Step

Step 0 → **Step 2**（除外フィルタ）→ Step 3（持ち込みのみ。昇格は `ideas/` に翻案済みなのでスキップ可）→ **Step 4**（競合チェック）→ Step 5（絶対判定）→ **Step 6**（ジョブ分析）→ Step 7 → Step 8 → Step 9 → Step 10 → Step 11

太字の3つは指名でも省かない。ゲーム・ネットワーク効果前提・強い競合を見逃すと、PRD を書き上げた後に作れないことが判明する。

### 停止条件（PRD 化せず判断を仰ぐ）

以下に当たったら PRD を書かず、**issue に `🤖` で始まるコメントで懸念と根拠を提示して止まる**。issue はクローズしない — ボツにするかはユーザーが決めることであり、指名を出した本人の意志を bot が上書きしてはいけない。

| 停止する理由 | コメントに書くこと |
|---|---|
| `config.yml` の除外条件に該当 | どの条件に、なぜ当たるか |
| 強い競合がいる（Step 4 の基準） | 競合アプリ名・評価件数・最終更新日 |
| スコアが `nomination_min_score` 未達 | 100点満点の内訳と、どの軸が足を引っ張っているか |
| ジョブ分析（Step 6）の関門で落ちる | どの項目で落ちたか（人気の因果仮説が「(c) マーケが上手いだけ」しか立たない／日本に同じジョブが存在しない 等） |
| `rejected/` に同じネタがある | 過去の却下理由と日付 |
| 昇格元の見送り理由が未解消 | 見送り理由と、それが今も成立している根拠 |

コメントの末尾には必ずこう添える:

```
この懸念を承知の上で進める場合は、この issue に返信してください。
返信があれば次回の実行でPRD化します（懸念はPRDの「リスクと検証ポイント」に明記します）。
```

ユーザーの返信（`🤖` で始まらないコメント）があれば、次回は**懸念を承知した判断**として扱い、停止せずPRD化する。懸念の内容はPRDの「リスクと検証ポイント」にそのまま残す。

### PRD 化する場合の差分

- **Step 9（記帳）の例外**: 昇格元の `ideas/{slug}.md` の削除は、main ではなく **PRブランチに含める**。通常の記帳を main 直コミットにしているのは「PRが却下されても記帳が消えないように」だが、`ideas/` の削除は却下されたら巻き戻ってほしい変更なので PR 側が正しい（マージ=昇格確定で消える／クローズ=ボツで `ideas/` に残る）
- **Step 10（PR）**: PR本文の冒頭に「指名元: #N（`ideas/` からの昇格 / 持ち込み）」を書き、`Closes #N` を入れる（マージ時に issue が自動で閉じる）。PRを作ったら issue に `processed` ラベルを付け、PRリンクを `🤖` コメントで残す（再検知の防止）
- **Step 11（Slack）**: 「指名（issue #N）由来」と1行入れ、週次の自動提案と区別できるようにする

## 改訂モード（PRコメントへの対応）

prd-vault のPRにユーザーからコメントが付いている場合:

1. `gh pr view {番号} --comments` でコメントを読む
2. 指示に沿ってPRDを改訂し、同じブランチに commit & push
3. 対応内容の要約をPRにコメントで返す。**コメントは必ず `🤖` で始める**（承認チェックジョブが bot 返信とユーザー指示を区別するマーカー）
4. Slackに「改訂しました」と短く通知
