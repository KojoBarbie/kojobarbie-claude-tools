# App Idea Hunt

海外市場のトレンドから「日本の個人開発者が1〜2週間で作れて、確実に収益が上がる」アプリのネタを発掘し、PRD（要件定義書）として `prd-vault` にPR提出するまでを自動で行う。

**このパイプラインの成果物はPRD 1本のPR（トンマナ3案＋触れる紙芝居モック＋PRD 本文の showcase ページ込み）**。ユーザーはPRをマージ（=Go）またはクローズ（=ボツ）するだけでよい（＋任意でトンマナ案を1文字返す）。その体験を壊さないよう、途中でユーザーへの質問はせず、判断はこのスキルの基準に従って自分で下す（例外は指名モードの停止条件だけ — そこでも同期的に聞くのではなく issue にコメントを残して終了する）。

## 起動モード

最初にどのモードで呼ばれたかを判定する。どのモードでも Step 0（準備）は必ず通り、成果物の形（PRD の PR + イベント1件）は同じ。

| モード | 起動条件 | 通す Step |
|---|---|---|
| **hunt**（既定） | 週次の自動実行、「ネタを探して」など対象が指定されていない依頼 | Step 0 〜 11（全部） |
| **nominate**（指名） | prd-vault に `idea` ラベルの open issue がある、または「`ideas/○○` を PRD にして」「このアイデアを回して」と特定のネタを指定された | Step 0 → Step 2 → **Step 2.5** → Step 4 〜 11（Step 1 の発散だけスキップ）。詳細は末尾の[指名モード](#指名モードidea-ラベルの-issue--手元のアイデア) |
| **revise**（改訂） | prd-vault のオープンPRにユーザーのコメントが付いている | 末尾の[改訂モード](#改訂モードprコメントへの対応) |

## 前提

**最初に `~/.config/app-factory/config.env` を読み込む**（`[ -f ~/.config/app-factory/config.env ] && . ~/.config/app-factory/config.env`。無ければ各変数は括弧内のデフォルト値を使う）。

| リソース | パス |
|---|---|
| PRDリポジトリ | `$PRD_VAULT_DIR`（デフォルト: `~/dev/business/prd-vault`。GitHub: `$GITHUB_OWNER/$(basename "$PRD_VAULT_DIR")`、デフォルトブランチ `main`） |
| 設定 | prd-vault 内の `config.yml` — 本数・スコア重み・注目カテゴリ・除外条件。**毎回最初に読む** |
| PRDテンプレート | prd-vault 内の `templates/PRD_TEMPLATE.md` |
| イベント記録 | `. "$APP_FACTORY_HOME/scripts/lib/events.sh"` して `emit_event`（仕様は `docs/events.md`）。**通知はしない** |
| 競合チェック | `bash {skill_dir}/scripts/jp_appstore_search.sh "検索語" [limit] [country]` |

## Step 0: 準備

1. `cd "$PRD_VAULT_DIR" && git checkout main && git pull`
2. `config.yml` を読み、本数・重み・注目カテゴリ・除外条件を把握する
3. **重複回避リスト**を作る: `prd/` `ideas/` `rejected/` の全ファイル名と各ファイル冒頭の概要、および `gh pr list --state all --limit 50` のPRタイトルを確認。過去に提案・却下したものと同じネタを再提案しない（`rejected/` は却下理由も読む — ユーザーの好みの学習データとして最重要）
   - **指名モードでは、指名された候補自身は重複回避の対象にしない**（`ideas/` にあるものを昇格させるのが目的なので、「既にある」を理由に弾いてはいけない）。ただし `rejected/` に同じネタがあった場合は却下理由を読み、指名モードの停止条件に従って判断を仰ぐ
4. **`rejected/` の復活枠を見る**: 却下理由が **競合・参入乱立だけ**のもの（「参入乱立」「競合あり」「後追い」等）は、Step 4 の基準を緩めた現在では通過する可能性がある。候補が足りないときの再評価対象として拾ってよい（その場合は Step 4 を新基準で必ずやり直す）。一方、**除外条件（SNS系・ゲーム・マネタイズ不可・規模超過）やジョブ分析で落ちたもの、ユーザーが明示的にボツにしたものは復活させない**

## Step 1: リサーチ（発散）

海外市場から候補を **10〜20個** 集める。1つの情報源に頼ると偏るので、必ず複数の切り口を使う。具体的な情報源と手順は [references/research-sources.md](references/research-sources.md) を読むこと。

`config.yml` の注目カテゴリ（課金されやすい=「課金した先に得られる未来」が想像しやすいカテゴリ）を重点的に探す。ただし発散フェーズなのでカテゴリ外の有望株を捨てる必要はない — 加点で差が付くだけ。

集める情報: アプリ名 / 国・ソース / カテゴリ / 規模感 / 収益モデル / **どんな機能があるか**。

**機能は必ず精査する**（2026-08-12 追記）。「何が受けているか」を雰囲気で1行書いて終わりにしない。ストアの説明文・スクリーンショット・レビューから**画面と機能を具体的に列挙する**（例:「バーコードスキャン→3Dオブジェクト出現」「開栓日と残量%を持つ」「就寝時の残量を計算して表示」）。ここで機能を取っておかないと Step 2.5 の比較表が作れず、以降の判定が規模（評価件数）だけになる。

収益モデルは買い切りに寄せずに拾う。**無料+サブスク / 無料+広告 / フリーミアム** も同じ重みで集める（`references/research-sources.md` の top-grossing チャート）。

`$APP_FACTORY_HOME` 内で実行されている場合は `/overseas-app-trends` スキル（Apptopia・Google Trends等の取得手順）も活用できる（作者環境にあるスキルの前提。無い環境ではスキップしてよい）。

## Step 2: 除外フィルタ

`config.yml` の `exclusions` を各候補に適用する。特に:

- **ネットワーク効果前提（SNS・マッチング・コミュニティ等）は即除外**。ユーザーが集まらないと価値が出ないアプリは、集客リソースのない個人開発者が最も失敗しやすい類型
  - **例外**: カップル向け・家族向けなど「既にいる特定の相手を1人招待すれば価値が成立する」クローズドアプリはネットワーク効果に当たらないので除外しない（2人だけの閉鎖型SNS等）。不特定多数を集めるマッチングは引き続き除外
- **ゲームは全ジャンル除外**
- **マネタイズの型が1つも当てはまらないものは除外**。ただし「なんとなく課金されなさそう」で切らない。買い切り / 無料+サブスク / 無料+広告 / フリーミアム の4つを順に当ててみて、`config.yml` の `business_context.unit_targets` に届く型が1つも書けないときだけ除外する。型が書けるならそれが薄くても除外せず、Step 5 の点数で表現する
- 1〜2週間のMVPに収まらない規模、医療診断・金融助言など審査/法規制リスクが高いものも除外
- **LLM のテキスト生成は除外理由にしない**（2026-08-12 改訂）。原価が高いのは画像生成・動画生成・音声合成の従量課金であって、LLM のテキストは1リクエスト0.1円オーダーで2桁違う。むしろ新しい価値を出すための前提技術として積極的に使ってよい。旧「サーバー費が収益を食う構成」という条項は範囲が広すぎて LLM 利用だけを理由に3件を却下していたため廃止した

除外した候補のうち「惜しかったもの」は理由とともにメモしておく（Step 9 で `rejected/` に記録する）。

## Step 2.5: 海外での機能比較（日本を見る前にやる）

**2026-08-12 新設。このパイプラインで最も重要な追加。**

Step 2 を通過した候補を、ここで **5〜10本**（多くても10本）に粗く絞る。そのうえで、**残った候補1本ごとに、海外の同ジャンル競合を 5〜10本** 調べ、**機能軸で比較表を作る**。

### なぜやるか

これをやらないと、候補の良し悪しを測る軸が「評価件数」しか無くなる。実際、2026-08-11 までの `rejected/` 102件のうち競合を理由に落とした54件は、そのほぼ全てが評価件数を根拠にしていた（発動の中央値5,173件。当時の基準が目安としていた10万件を大きく下回る）。**機能という比較可能な軸を先に作ることで、以降の判定を規模から切り離す。**

### やること

1. 候補アプリと同ジャンルの海外アプリを 5〜10本リストアップする（`jp_appstore_search.sh` の country を us / gb / de / kr などに変えて叩く）
2. **機能を列で持つ比較表**を作る。行がアプリ、列が機能。列は自分で定義する（例: バーコード入力 / 手動入力 / 残量管理 / コレクション表示 / 統計 / ウィジェット / 同期）
3. 各アプリについて **「こいつはこの機能があるから強い / 新しい」を1行**で書く。ここが空欄になるアプリは、単なる同型の後追いなので候補として弱い
4. **より強いアプリが見つかったら、そちらに乗り換えてよい**。Step 1 のピックは確定ではなく仮説として扱う。「元ネタの競合の方が新しくて良い」は歓迎すべき発見であって、やり直しではない
5. 各機能について **その機能がどのジョブを解いているか**を1行で書く（→ 次項）

### ジョブ分解をここで回す

Step 6 のジョブ分析4項目のうち、**ジョブ分解だけをこの Step に前倒しする**（2026-08-12）。理由は、**機能を理解するための手段としてジョブ分解が要る**から。「この機能はどのジョブを解いているか」が書けて初めて、機能比較が意味を持つ。

- ここでやるのは **機能 → 解いているジョブ** の対応付けだけ。残り3項目（人気の因果仮説 / 日本への移転可能性 / KPI設計）は Step 6 のまま
- 候補ごとに回すとコンテキストが膨らむので、**候補1本＝サブエージェント1つ**で並列に投げる。返してもらうのは比較表と「強み1行」「解いているジョブ1行」だけ
- この結果は `ideas/` にも `rejected/` にも短く残す（Step 9）。全文は要らない — **解いているジョブ1行と、それを担う機能名**が残っていればよい

### 出力

候補ごとに: 機能比較表 / 最も強いアプリとその理由1行 / 乗り換えの有無 / 各機能が解いているジョブ。これを Step 3 以降に引き渡す。

## Step 3: 日本展開への翻案

Step 2.5 で選び直した候補それぞれについて「日本の個人開発者として出すならどうなるか」を1〜3行で構想する。

**まず「そのまま持ってくる」を基準線に置く**（2026-08-12 改訂）。海外で流行っているならそのまま出してよい。そのうえで、日本の文脈（習慣・季節・制度・既存アプリの不満）に合わせて変えるならどうなるかを書く。

**ここは原則として脱落ゲートにしない。**「日本に習慣が無い」を理由に落とすのはやめる — 代わりに**乗り越えるべき壁を特定し、越えられるかを判断する**。壁は必ずあるので、それを書き出すのがこの Step の仕事になる。

ただし次の1つだけは脱落させる:

- **価値の本体が海外の制度・規格そのもので、日本に置き換えられないもの**。例: 米国 NEC 規格の電気工事リファレンス、英国の運転免許学科試験。これは翻案ではなく作り直しになり、しかも作者に検証手段が無い

## Step 4: 競合チェック（日本App Store）

各候補について、想定される検索語 **2〜3語**（日本語・英語両方）で調査する:

```bash
bash {skill_dir}/scripts/jp_appstore_search.sh "睡眠 記録" 10 jp
```

**2026-08-12 改訂: 判定を「規模」から「機能の一致」に全面的に置き換えた。**

Step 2.5 で海外の機能比較表を作ってあるので、**同じ列で日本のアプリを並べる**。ジャンルや評価件数ではなく、比較表の埋まり方を見る。

### 脱落条件（この1つだけ）

**「機能セットがほぼ一致」× 「その競合が実際に使われている」の両方に当てはまるときだけ脱落**させ、`rejected/` に競合名と一致した機能を書く。

- *機能セットがほぼ一致* = Step 2.5 の比較表で、**コア機能の列が埋まり方まで重なる**。ジャンルが同じ・カテゴリが同じ・「なんとなく似ている」は一致ではない。**機能軸で見れば完全一致はそう頻繁には起きない**ので、迷ったらそれは一致していない
- *実際に使われている* = レビューが積み上がっている、または更新が継続している。**評価0〜数件の新規アプリは、機能が一致していても無視してよい**（まだ誰にも使われていないため）

### 脱落理由にしないもの

以下はいずれも通過。競合の「隙」は PRD の差別化欄に使う。

- **評価件数の多さそれ自体**。何万件あっても、機能が違うなら関係ない。ここが従来の最大の誤用ポイントだった
- **「参入乱立」（評価0〜数件の新規が同ジャンルに何本も出ている）**。むしろ同じネタに複数人が張っていることは需要の傍証として扱う
- **無料の巨人がいること**。無料アプリと有料アプリは同じ財布を奪い合っていない。参考元が有料だからといって、無料competitorの規模で落としてはいけない
- 更新停止、UXが古い、日本語対応が雑、価格設定が強気
- 同ジャンルだがターゲット・切り口・使う場面がずれている

**競合ゼロ** → 通過だが「なぜ誰もやっていないのか」を一度疑う（需要がない可能性・技術/審査上の壁）。理由に納得できたら通過。

### 収益モデルの空きも見る

競合の評価件数ではなく、**その検索語に「どの収益モデルが埋まっていて、どれが空いているか」**を記録する。買い切りが1本もいない／サブスクが誰も取っていない／無料の広告モデルだけ、といった状態は Step 5 の monetization の材料になる。買い切り前提に寄せず、無料+サブスク・無料+広告・フリーミアムも同じ土俵で見る。

迷ったら通過させる。この段階で候補を絞りすぎるとネタが枯れる。

## Step 5: スコアリングと選定

通過候補を `config.yml` の `scoring` の重みで100点満点採点し、表にまとめる。上位 `prds_per_run` 本をPRD化し、次点 `ideas_to_stock` 本を `ideas/` にストックする。

**指名モードでは相対比較が成立しない**（候補が1件なので必ず1位になる）。上位N本を選ぶ代わりに、`config.yml` の `pipeline.nomination_min_score`（デフォルト60）を通過ラインとした絶対判定に切り替える。未達なら PRD 化せず、点数の内訳と弱点を添えて判断を仰ぐ（指名モードの停止条件を参照）。

**このステップで足切りするのではなく順位を付けるのが目的**である（足切りは Step 2 の除外条件、Step 4 の機能一致、Step 6 のジョブ分析が担う）。

### 配点（2026-08-12 改訂）

`market_gap` を最大配点にし、`buildability` と `personal_fit` を下げ、`monetization` を絶対量判定に変えた。重みの実体は `config.yml` を読むこと。

| 軸 | 配点 | 採点の仕方 |
|---|---|---|
| **market_gap** | **35** | **規模ではなく機能の重複度で付ける。**Step 2.5 / Step 4 の比較表で、コア機能の列がどれだけ空いているか。評価件数は根拠に使わない |
| monetization | 25 | **絶対量で付ける。**下記参照 |
| buildability | 20 | 1〜2週間でMVPが出るか |
| aso_clarity | 15 | どの検索語で見つかるか。その語を既に検索しているか |
| personal_fit | 5 | 既存アプリ群との相性。実務上ほとんど差が付かないので小さい |

### monetization は定性判断を禁止する

「支払い意欲がありそう」で付けない。`config.yml` の `business_context.unit_targets` を見て、**次のどれか1行を必ず書く**:

```
¥800 買い切り → 手取り¥680 → 月15本で ¥10,200/月（最低ライン ¥10,000 をクリア）
```

- 埋まらない、あるいは必要量が現実離れしている（例: DAU 500 が要る）ものは大きく減点する
- **買い切りに寄せない。**無料+サブスク / 無料+広告 / フリーミアムも同じ土俵で計算する。Step 4 で記録した「その検索語で空いている収益モデル」をここで使う
- 加えて「**課金した先に得られる未来**」が一言で言えるかを確認する（例: 英語が話せるようになる / 痩せる / 仕事の工数が減る）。言えないものは辛めに付ける

## Step 6: ジョブ分析（PRD化の関門）

スコアリングで選ばれた候補を、PRDに落とす前に**ジョブ理論で分析**する。分析に耐えない候補はスコアが高くてもここで落とす（`ideas/` に理由付きで残す）。

**2026-08-12 改訂: 1.（ジョブ分解）は Step 2.5 に前倒し済み。**機能を理解する手段として、候補ごとに既に回してある。この Step ではその結果を**引き継いで深める**だけで、ゼロから始めない。前倒しの狙いは、ここで初めて落ちる候補を減らすこと — 機能比較の段階でジョブが見えていれば、そもそも弱い候補は Step 2.5 で乗り換えられている。

1. **ジョブ分解**（Step 2.5 から引き継ぎ）: 機能ごとに書いた「解いているジョブ」をまとめ、「機能的/感情的/社会的ジョブ」と「誰が・どんな状況で・何の代わりに雇うか」に整形する。代替品は同カテゴリアプリに限定しない（紙・我慢・人への依頼を含める）
2. **人気の因果仮説**: なぜ海外で人気/急上昇なのかを、(a) ジョブ自体が新しく生まれた、(b) 既存ジョブの解決コストを下げた、(c) マーケが上手いだけ、のどれかに分類し根拠を示す。(c) しか説明が立たない候補は原則落とす。急上昇ネタはきっかけ（バイラル・特集・季節性）と再現可能性を必ず評価する
3. **日本への移転可能性**: 同じ状況・同じジョブが日本に存在するか、既に支配的な代替解決手段がないか、サービス側で調整が必要な点は何かを検証する。ジョブが日本に存在しない/別の解決が支配的なら落とす
4. **KPI 設計**: コア行動を1つ定義し、収益に至る KPI ツリー・計測イベント一覧・マイルストーン（M1〜M3）・見送り基準を決める。数値目標は必ず具体化する:
   - M1〜M3 の基準値は**グローバル初期値の丸写し禁止**。カテゴリの一般的な水準・元ネタアプリの実績・想定市場規模から、このアプリ固有の数値を**根拠1行付き**で設定する
   - 収益目標は「**収益化手段 × 想定転換率 × 必要ユーザー数**」の算数を1行書く（例: 買い切り¥600 × 転換率3% × 月間DL 300 ≈ 月¥5,400）

## Step 7: PRD執筆

選ばれた候補について追加リサーチ（参考元アプリのレビュー・価格・機能詳細、必要な技術の実現性）を行い、`templates/PRD_TEMPLATE.md` の全セクションを埋める。

- ファイル名: `prd/{english-slug}.md`（例: `prd/sleep-streak.md`）
- **「ジョブ分析」「KPIと計測計画」の2セクションを必ず埋める**（Step 6 の分析結果をそのまま落とす）。セクション定義は [references/prd-sections.md](references/prd-sections.md)。prd-vault のテンプレートにこの2セクションが無ければ、この references の内容で PRD に直接書く（テンプレート自体の更新も1回だけ提案してよい）
- 全セクションを具体的に書く。「〜を検討する」のような先送りは書かない — このPRDだけを読んで開発を開始できる状態にする
- マネタイズ欄は必ず金額まで書く（価格、想定DL数、月次収益見込みの逆算）。加えて「このアプリを使い続けたらユーザーがどう変わるか」を1行で書く — 課金設計は機能を売るのではなく未来の変化を見せるのが軸。ペイウォールの訴求文言もこの1行から作る
- **課金の実装基盤は RevenueCat を既定とする**（StoreKit を直叩きしない）。買い切り・サブスクいずれでも RevenueCat の Offering／Entitlement で管理する前提で「技術メモ」に書く。理由: レシート検証・購入復元・クロスデバイス同期を肩代わりでき、後からサブスク化や価格ABテストに拡張しやすい。無料プラン（追跡月商 $2,500 まで無料）の範囲なので個人開発でも実質コストゼロ
- 「デザイン方向性メモ」は後続の `app-kickoff` がコンセプトシートを作る際の入力になるので、世界観が想像できる程度に書く。**Step 8 で作るトンマナ3案のうち「推し案」と一致させ、どの案を推しているかをメモに明記する**（ユーザーが別案を選んだら、改訂モードでこのメモを差し替える）
- **「感動する1点」を1行書く**（`app-design-craft` のレンズ9）。このアプリで最も気持ちいい瞬間はどこで、何で心が動くか。ここが Step 8 のモックで演出を厚くする箇所になり、実装でも最優先で磨く箇所になる。機能一覧からは出てこないので、ジョブの感情的側面から書く

## Step 8: トンマナ・モック・PRD ページ（showcase）

PRD化する案ごとに、prd-vault の `showcase/`（Next.js App Router・静的エクスポート・**Vercel** デプロイ前提。LP は Firebase Hosting のままなので混同しない）へ確認用のページを作る。**PRDと同じブランチ・同じPRに含める**（コミットは Step 10 で行う）。`ideas/` 止まりの案には作らない。

ディレクトリ構成・apps.json スキーマ・各ページの要件・ブートストラップ手順は
[references/showcase-spec.md](references/showcase-spec.md) を**必ず読んでから**作る。
紙芝居の共通部品コードは [references/prototype-kit.md](references/prototype-kit.md)。

### 8-1. 先に実例を見る

この案のカテゴリ・狙う気分に近いアプリを実際に見る。
**方向性の異なるものを混ぜて見ること**（同系統ばかり見ると3案が3案にならない）。
該当が無ければ `app-design-craft` の原則だけで進める — それは劣化ではない。
参照画像を使う場合は `showcase/public/refs/` にコピーして参照する。

### 8-2. 作るページ（4つ）

| ページ | 中身 |
|---|---|
| `app/apps/{slug}/page.tsx` | ハブ。3案・モック・PRD への導線 |
| `app/apps/{slug}/tone/page.tsx` | **トンマナ3案**。方向性を明確にずらした3案を並べ、推し案を明示する |
| `app/apps/{slug}/mock/page.tsx` | **触れる紙芝居モック**。4〜6画面、ボタンで実際に遷移する |
| `app/apps/{slug}/prd/page.tsx` | PRD 本文（`prd/{slug}.md` を読んで描画。二重管理しない） |

`showcase/apps.json` に `{ slug, name, status, prd, createdAt, toneChosen: null }` を追記する。

**譲れない点（ここを緩めると凡庸なアプリになる）**:

- **トンマナは1案でなく3案**。1案だとそれが自動的に正解になり、毎回同じ方向に寄る。
  色違いは3案ではない — ずらすのは世界観の核。各案に「向くジョブ / 向かないジョブ」を1行ずつ
- **3案は `app-design-craft` の⓪の8方向から、異なる3方向を選ぶ。** 方向名を各案に明記する:
  `calm/serene` `playful/energetic` `premium/refined` `utilitarian/focused`
  `editorial/magazine` `brutalist/raw` `warm/organic` `cold/technical`
  （詳細は `dev-workflow-tools:app-design-craft` の `references/design-decisions.md` ⓪）
- **直近2本のアプリが使った方向は3案の候補から外す。** `$PRD_VAULT_DIR/portfolio.yml` の
  新しい順に2本を見て、その `docs/design-concept.html` の方向性を確認する。
  この制約が無いと「ずらした3案」が実際には calm の濃淡3つになり、どれを選んでも同じ顔になる
  （2026-08 実測: 11本中9本がオフホワイト・紙・静かに収束していた）
- **モックは静止画ではなく触れる紙芝居**。ボタンを押すと次の画面へ遷移し、
  「押す→こう遷移する→ここで記録される」を指で辿れること
- **山場を必ず含める**: 初回起動（データ0件）/ コア行動 / **完了・達成の瞬間** / 空状態
  （＋収益化があればペイウォール）。時間が無いなら画面数を4に減らす — **山場ではなく周辺を削る**
- **完了の瞬間に演出を入れる**（0.4〜0.8秒）。気持ちよさは静止画に写らないので、
  静止画だけのモックからは気持ちいいアプリは生まれない
- **コピーとデータは実物**。「テキスト」「サンプル1」の類を1つも残さない
- **「ダークモード禁止」を「明るい配色にしろ」と読み替えない。** 規約の意味は
  **単一外観（ライト/ダークの2系統を作らない）**であって、その1つの外観が暗くてもよい
  （実例: Tanamori は `#0C0B0A` の単一ダーク外観）。ここを取り違えると
  premium/refined・cold/technical・brutalist/raw の3方向が構造的に選べなくなり、
  ポートフォリオがオフホワイト一色になる。**showcase のページ自体は明るく作る**（これは別の話）

> このモックは「確認用の簡易表示」ではなく、**実装が目指す目標値**。
> モックが最低限なら完成品は必ずそれ以下になる。

### 8-3. 確認

- `showcase/` が存在しなければ references の手順で最小構成をブートストラップする。Vercel プロジェクト（`pv-showcase-12ced869`）は接続済みなので、人間の接続作業は不要
- 作成後、`showcase/` で `npx next build` が通ることを確認する（`node_modules` が無ければ先に `npm install`）
- `references/prototype-kit.md` 末尾のチェックリストで自己点検してから次へ進む

## Step 9: 記帳（main に直接コミット）

PRD本体より**先に**、ブックキーピングを main に直接コミットして push する:

- `ideas/{slug}.md` — 次点候補。3〜5行の概要＋スコア＋見送り理由
- `rejected/{slug}.md` — 除外・脱落した候補。1〜3行の概要＋却下理由（`機能一致: {アプリ名}（一致した機能）` / `SNS系` など）

**どちらにも Step 2.5 のジョブ分解を1行だけ添える**（2026-08-12 追記）。形式は「解いているジョブ ← それを担う機能名」。全文は要らない — 後から「このネタは何を解こうとしていたか」が引ければ十分なので、記帳が肥大しない程度に留める。

却下理由に競合の評価件数を根拠として書かない。書くのは**一致した機能名**と、その競合が稼働しているかどうか。

これらをPRブランチに入れると、PRが却下されたときに記帳まで消えてしまう。必ず main 側に分けること。

## Step 10: PRD のPR作成

```bash
git checkout -b prd/{slug}
git add prd/{slug}.md showcase/ && git commit -m "PRD: {アプリ名（仮）}"
git push -u origin prd/{slug}
gh pr create --title "PRD: {アプリ名（仮）} — {一言コンセプト}" --body "..."
```

PR本文の冒頭に、レビュー観点を明記する:

```
このPRのレビューで見てほしいのは「ジョブ分析」と「KPIと計測計画」です。
機能や技術ではなく、①ジョブ分解が納得できるか ②人気の因果仮説が信じられるか
③日本への移転可能性の検証が甘くないか ④KPIに具体的な目標数値と根拠が入っているか、
を判断してマージ/クローズ/コメントしてください。
マージ = M1未達なら maintain 行き、という見送り基準への合意も含みます。

トンマナは3案あります。推しは A 案（PRD もA案で書いています）。
別の案がよければ「Bで」の1語だけコメントしてください（マージ後の app-kickoff がそれで作ります）。
無言でマージ = 推し案の採用です。
```

続けて: 一言コンセプト / 総合スコアと内訳 / 想定月次収益 / 競合チェック結果の要約 / **showcase の3リンク（トンマナ3案・モック・PRD本文）** / 「マージ=Go、クローズ=ボツ、コメント=修正指示」の操作ガイド、を含める。ドラフトにはしない（マージ操作が承認フローなので、マージ可能な状態で出す）。

## Step 11: イベント記録

**通知はしない。** PRD が1本できたことをイベントに残すだけで、誰にどう知らせるかは利用者の受け手が決める。

```bash
. "$APP_FACTORY_HOME/scripts/lib/events.sh"
EVENT_JOB=app-idea-hunt
emit_event kind=proposal_opened severity=action app="<アプリ名>" \
  title="<一言コンセプト>（スコア N / 想定月次 ¥X）。マージ=Go、クローズ=ボツ、コメント=修正指示" \
  url="<PR URL>" score=N revenue_est=X
```

`title` に長文を貼らない — 詳細は PR リンク先で読んでもらう。

showcase の確認先も添える:

- PR を上げると Vercel が**プレビューを自動デプロイして PR にコメント**するので、基本は「PR のプレビューリンクから確認」と案内する。プレビュー URL は Vercel ログインが必要（Vercel Authentication）
- PR 作成直後でプレビュー URL がまだ取れていない場合に備え、マージ後の本番 URL
  `https://pv-showcase-12ced869.vercel.app/apps/{slug}` （ハブ。ここからトンマナ3案・モック・PRD 本文へ行ける）も併記する
- モックについては「**ボタンを実際に押して最後まで辿れます**」と1行添える（静止画だと思われると触ってもらえない）
- トンマナは「3案あります。別案がよければ『Bで』とPRにコメント」と1行

## 収穫ゼロのとき

全候補が基準を満たさなかった場合、無理にPRDを出さない（質の低い提案はパイプラインの信頼を毀損する）。`rejected/` への記帳だけ行い、`kind=job_finished` / `severity=info` のイベントに「今週は基準を満たすネタがなかった」と主な脱落理由を書く。

ただし**収穫ゼロにする前に、脱落理由の内訳を数えて自己点検する**（2026-08-12 改訂: 定性表現をやめて手順にした）。

1. 今回の脱落を Step 別に数える
2. **Step 4（競合）で落ちた件数が全体の半分を超えていたら、その候補群を全部見直す。** 見直しの観点は「機能セットが本当に一致していたか」「一致した競合は実際に稼働していたか（評価0〜数件の新規ではなかったか）」の2点だけ
3. 却下理由に**競合の評価件数しか書いていないものがあれば、それは判定になっていない**ので必ず差し戻す。書くべきは一致した機能名

収穫ゼロが妥当なのは、除外条件（SNS系・ゲーム・マネタイズの型が書けない）やジョブ分析で落ちた候補が大半のときだけ。

（これは hunt モードのルール。指名モードで候補が基準を満たさなかった場合は「指名モードの停止条件」に従う）

## 指名モード（`idea` ラベルの issue / 手元のアイデア）

`ideas/` に眠っている候補を昇格させたい、あるいは自分の手元にあるアイデアを同じ基準でリサーチ・採点させたいときのモード。**発掘（Step 1 の発散）をスキップする機能であって、審査を省略する機能ではない**。

### 入力の受け取り

```bash
gh issue list --repo "$GITHUB_OWNER/$(basename "$PRD_VAULT_DIR")" --label idea --state open \
  --json number,title,body,labels,comments
```

処理対象は「`processed` ラベルが無く、かつ（コメントが無い or 最終コメントが `🤖` で始まらない）」もの。最終コメントが `🤖` のものは判断待ちなのでスキップする。会話から指名された場合は issue 番号が無いだけで、以降の手順は同じ。

入力は2種類:

- **昇格** — `ideas/{slug}.md` が存在する場合。そのファイルを候補記述として使う（概要・スコア・見送り理由が既に書かれている）。**見送り理由が解消されているかを必ず再評価する**（例: 「hirune が一段落してから」なら `portfolio.yml` で hirune の現ステージを確認し、解消されていなければ停止条件として扱う）
- **持ち込み** — 対応する `ideas/` が無い場合。issue 本文／ユーザーの説明をそのまま候補記述として使う。参考元アプリや収益モデルが書かれていなければ、**その候補についてだけ** [references/research-sources.md](references/research-sources.md) の情報源で裏取りする（類似の海外アプリ・価格・実績を探す。10〜20個集める発散はしない）

### 通す Step

Step 0 → **Step 2**（除外フィルタ）→ **Step 2.5**（海外の機能比較）→ Step 3（持ち込みのみ。昇格は `ideas/` に翻案済みなのでスキップ可）→ **Step 4**（競合チェック）→ Step 5（絶対判定）→ **Step 6**（ジョブ分析）→ Step 7 → Step 8 → Step 9 → Step 10 → Step 11

太字の4つは指名でも省かない。ゲーム・ネットワーク効果前提・機能が完全に一致する競合を見逃すと、PRD を書き上げた後に作れないことが判明する。

**Step 2.5 は指名モードでも必ず回す**（2026-08-12 追記）。指名は「発掘をスキップする機能」であって、機能比較を省略する機能ではない。むしろ候補が1本しかない指名モードでは、海外の同ジャンルを並べて「この案より強い競合が既にいないか」を見る価値が大きい。ここでより強いアプリが見つかった場合は、乗り換えを提案する形で issue にコメントする（勝手に差し替えず、指名した本人の意志を確認する）。

### 停止条件（PRD 化せず判断を仰ぐ）

以下に当たったら PRD を書かず、**issue に `🤖` で始まるコメントで懸念と根拠を提示して止まる**。issue はクローズしない — ボツにするかはユーザーが決めることであり、指名を出した本人の意志を bot が上書きしてはいけない。

| 停止する理由 | コメントに書くこと |
|---|---|
| `config.yml` の除外条件に該当 | どの条件に、なぜ当たるか |
| 機能が完全に一致する稼働中の競合がいる（Step 4 の基準） | 競合アプリ名・**一致した機能名**・稼働の根拠（レビューの積み上がり／更新継続）。評価件数だけを根拠にしない |
| Step 2.5 で、この案より明確に強い競合が見つかった | その競合名と「強い理由（機能）」1行。乗り換えを提案する |
| スコアが `nomination_min_score` 未達 | 100点満点の内訳と、どの軸が足を引っ張っているか |
| ジョブ分析（Step 6）の関門で落ちる | どの項目で落ちたか（人気の因果仮説が「(c) マーケが上手いだけ」しか立たない／日本に同じジョブが存在しない 等） |
| `rejected/` に同じネタがある | 過去の却下理由と日付 |
| 昇格元の見送り理由が未解消 | 見送り理由と、それが今も成立している根拠 |

コメントの末尾には必ずこう添える:

```
この懸念を承知の上で進める場合は、この issue に返信してください。
返信があれば次回の実行でPRD化します（懸念はPRDの「リスクと検証ポイント」に明記します）。
```

ユーザーの返信（`🤖` で始まらないコメント）があれば、次回は**懸念を承知した判断**として扱い、停止せずPRD化する。懸念の内容はPRDの「リスクと検証ポイント」にそのまま残す。

### PRD 化する場合の差分

- **Step 9（記帳）の例外**: 昇格元の `ideas/{slug}.md` の削除は、main ではなく **PRブランチに含める**。通常の記帳を main 直コミットにしているのは「PRが却下されても記帳が消えないように」だが、`ideas/` の削除は却下されたら巻き戻ってほしい変更なので PR 側が正しい（マージ=昇格確定で消える／クローズ=ボツで `ideas/` に残る）
- **Step 10（PR）**: PR本文の冒頭に「指名元: #N（`ideas/` からの昇格 / 持ち込み）」を書き、`Closes #N` を入れる（マージ時に issue が自動で閉じる）。PRを作ったら issue に `processed` ラベルを付け、PRリンクを `🤖` コメントで残す（再検知の防止）
- **Step 11（イベント）**: `meta.origin=issue-N` を付け、週次の自動提案と区別できるようにする

## 改訂モード（PRコメントへの対応）

prd-vault のPRにユーザーからコメントが付いている場合:

1. `gh pr view {番号} --comments` でコメントを読む
2. **トンマナ案の選択（「Bで」「C案がいい」など）が含まれていたら**:
   - `showcase/apps.json` の該当エントリの `toneChosen` をその案（`"B"` 等）に更新する
   - tone ページの「推し」表示を選ばれた案に付け替える
   - **モックを選ばれた案の配色・角丸・タイポで作り直す**（モックは推し案で作ってあるため）
   - PRD の「デザイン方向性メモ」を選ばれた案の内容に差し替える
   - 以後 `app-kickoff` は `toneChosen` を見てコンセプトシートを作る
3. その他の指示に沿ってPRDを改訂し、同じブランチに commit & push
   （showcase を触ったら `npx next build` が通ることを確認してからコミットする）
4. 対応内容の要約をPRにコメントで返す。**コメントは必ず `🤖` で始める**（承認チェックジョブが bot 返信とユーザー指示を区別するマーカー）
5. `emit_event kind=proposal_opened severity=action` で「改訂しました」を短く残す
