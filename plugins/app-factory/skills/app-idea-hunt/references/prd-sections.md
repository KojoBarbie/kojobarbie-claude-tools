# PRD 必須セクション定義 — 「ジョブ分析」「KPIと計測計画」

PRD には以下の2セクションを**必ず**含める（Step 6 の分析結果をそのまま落とす）。

- prd-vault の `templates/PRD_TEMPLATE.md` にこの2セクションがあればテンプレートに従う
- 無ければ、このファイルの定義で PRD に直接書く。挿入位置は「デザイン方向性メモ」の**前**（以降のセクション番号は振り直す）。テンプレート自体への追加も**1回だけ**提案してよい（毎回提案しない）

---

```markdown
## 9. ジョブ分析（なぜ売れるか）

> このセクションが PRD レビュー（PR マージ判断）の主眼。
> 「機能が作れるか」ではなく「このジョブ分析が信じられるか」を人間がチェックする。

### 9.1 ジョブ分解

- **機能的ジョブ**: <ユーザーは何を片付けたくてこれを雇うか>
- **感情的ジョブ**: <使うことでどう感じたいか>
- **社会的ジョブ**: <どう見られたいか（該当すれば）>
- **雇用の状況**: 誰が・どんな状況で・**何の代わりに**雇うか
  （代替品は同カテゴリアプリとは限らない。紙のメモ・我慢・人への依頼なども含めて書く）

### 9.2 人気の因果仮説

- 元ネタが海外で人気/急上昇している理由: <ジョブが新しく生まれた（規制・流行・プラットフォーム変化）
  / 既存ジョブの解決コストを下げた / マーケが上手いだけ、のどれか。根拠と共に>
- 急上昇の場合のきっかけと再現可能性: <バイラル・特集・季節性など>

### 9.3 日本への移転可能性

- 同じ状況・同じジョブが日本に存在するか: <生活習慣・制度・文化の差分を明示>
- 日本で既に支配的な代替解決手段: <あれば。それでも勝てる理由>
- ジョブは同じでもサービス側で調整が必要な点: <決済感覚・トーン・ローカル制度対応など>

## 10. KPIと計測計画

> portfolio-review がこのセクションをそのままステージゲート判定に使う。

### 10.1 コア行動と KPI ツリー

- **コア行動**（このアプリの価値が発生する1行動）: <例: 昼寝タイマーを完了する>
- KPI ツリー: 収益 ← <収益化ファネル: 例 ペイウォール到達率×トライアル開始率×転換率>
  ← 継続（D1/D7）← アクティベーション（初回セッションでコア行動を完了した率）← DL
- **収益の算数**（1行必須）: <収益化手段 × 想定転換率 × 必要ユーザー数。
  例: 買い切り¥600 × 転換率3% × 月間DL 300 ≈ 月¥5,400>

### 10.2 計測イベント一覧（Firebase Analytics）

| イベント名 | 発火タイミング | 対応する KPI |
|---|---|---|
| `core_action_completed` | <コア行動の完了時> | アクティベーション / 継続 |
| `paywall_viewed` | <ペイウォール表示時> | 収益化ファネル |
| <追加イベント> | | |

### 10.3 マイルストーンと見送り基準

| | 期日 | 基準（このアプリ固有の数値） | 根拠（1行） |
|---|---|---|---|
| M1 | リリース +4週 | <例: DL 累計 ≥ 300 / アクティベーション ≥ 45% / D1 ≥ 20%> | <カテゴリ水準・元ネタ実績・市場規模のどれに基づくか> |
| M2 | リリース +8週 | <収益初発生の定義、または DAU 目標と傾向> | |
| M3 | リリース +16週 | <月次収益目標> | |

- **見送り基準**: 8週経過で M1 未達なら maintain へ（このPRDの承認＝この基準への合意）
```

---

## KPI 数値の書き方（必須ルール）

- M1〜M3 の基準値は**グローバル初期値の丸写し禁止**。グローバル初期値（M1: DL≥100 / アクティベーション≥40% / D1≥15%、M2: 収益初発生 or DAU≥10 で増加傾向、M3: 月次収益≥5,000円）は下限の参考にとどめ、カテゴリの一般的な水準・元ネタアプリの実績・想定市場規模から**このアプリ固有の数値**を導き、根拠を各行に1行書く
- 収益目標は「収益化手段 × 想定転換率 × 必要ユーザー数」の算数を必ず1行書く（10.1）。この算数と 10.3 の M3 が矛盾しないこと
