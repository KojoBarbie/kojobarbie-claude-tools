# 監査観点: テスト・CI・可観測性・リリース体制

## テスト

1. レイヤー別のカバー状況（data/domain/presentation、サーバー側）と**テストゼロの画面/モジュール一覧**
2. サーバーコードは src と test のファイル数比較でクリティカルパスの穴を見る（通知・認証・課金まわりは特に）
3. golden/スクリーンショットテスト、統合テスト（主要導線1本があるか）の有無
4. カバレッジの**主張と計測の整合**（「90%」と言っているのに計測設定がどこにもない、は頻出）

## CI

1. PR/push で何が走るか（test・lint・format・analyze/型チェック）。
   pre-commit フックにしかない検査は CI にも置く（フック未導入環境がすり抜ける）
2. カバレッジゲート、Dependabot / 依存監査の有無
3. **サーバーサイドのデプロイ CI の有無**（手動デプロイのみ、は「テスト済みコードと本番の乖離」の温床。
   配線漏れバグが本番に残り続けた実績あり）
4. workflow の無効化状態（`gh workflow list --all` で disabled_manually を確認 — 気づかず放置されていた実績あり）
5. self-hosted runner がある場合: fork PR のコード実行、シークレット露出、スクリプトインジェクション
   （PR タイトル・ブランチ名を直接シェルに埋めていないか）

## 可観測性

1. クラッシュレポート（Crashlytics 等）: 導入 + `FlutterError.onError` / uncaught handler への配線 + Logger 統合
2. Analytics: 画面遷移の自動計測、イベント定数の一元管理
3. **Performance Monitoring**: 起動時間・API 応答のカスタムトレース（パフォーマンス改善の効果検証はこれがないと主観になる）
4. サーバー側のエラーアラート: `console.error` 止まりでなく、スケジュールジョブ全滅に気づける通知経路があるか

## リリース体制

1. **アプリ本体のリリース runbook の有無**（ビルド → TestFlight/内部テスト → 提出 → 審査 → 段階的公開 → ロールバック）。
   「それらしい名前の文書が実は別物（LP 用等）」に騙されず中身を確認する
2. バージョニング戦略の一貫性（pubspec/プロジェクト設定と CI のビルド番号採番の関係が文書化されているか）
3. 段階的ロールアウト（App Store phased release / Play staged rollout）の方針
4. fastlane 等の署名・メタデータ管理（スクショ・説明文がバージョン管理されているか）

## ドキュメント

1. README と実態の乖離（実装済み機能が「予定」のまま、ツールのバージョン表記が古い）
2. 運用ドキュメント（監視ダッシュボードの導線、バッチ失敗時の確認手順）の有無
