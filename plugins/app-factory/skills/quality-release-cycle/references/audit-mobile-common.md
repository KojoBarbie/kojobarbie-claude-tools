# 監査観点: モバイル共通（UI/UX・ストア品質）

スタック（Flutter / iOS ネイティブ）によらず全アプリに適用する観点。
発見には必ず severity（高/中/低）・file:line・1行の修正案を付け、GOOD（既に良い実装）も列挙する。

## 画面の3状態 + オフライン

1. 全画面をインベントリ化し、**loading / error+再試行 / empty** の3状態が揃っているか画面ごとに確認する
2. エラー時のデッドエンド（「戻る」しかなく再試行できない画面）は他画面との一貫性欠如として指摘
3. オフライン検知の有無（connectivity 監視、オフラインバナー、再接続時の自動リトライ）
4. pull-to-refresh の有無（リスト系画面）

## ナビゲーション

1. ルーターのエラーフォールバック（未知ルート・不正な ID パラメータでの遷移先）。
   **プッシュ通知のディープリンク経由で不正 ID が来るケース**は実在するので、受け側の堅牢性を必ず見る
2. Android ハードウェアバック / iOS スワイプバックでの誤離脱（入力途中の画面に確認ダイアログがあるか）
3. オンボーディング・初期設定フローの離脱経路（途中で閉じたらどうなるか）

## ビジュアル一貫性

1. カラー・フォント・spacing の直書き箇所数を grep で数え、テーマ/デザイントークン参照との混在度を測る
2. ダークモード対応の有無（テーマ定義と、OS 設定への追従）。
   夜間利用が想定されるアプリ（日記・睡眠・リラックス系）では優先度を上げる
3. フォントの二重管理（画面によって直指定とテーマ参照が混在していないか）

## アクセシビリティ（監査対象外 — 見つけても Issue 化しない）

**支援技術・アクセシビリティ設定に固有の観点は、この監査では見ない。** 対象外なのは次の類:

- Dynamic Type / テキストスケーリング追従（`relativeTo:` / `@ScaledMetric` の有無）
- VoiceOver・TalkBack・semantic ラベル / accessibilityAction
- WCAG のコントラスト比（4.5:1 / 3:1）達成可否
- Reduce Motion 対応
- タップ領域の 44/48pt 基準への適合

理由は SKILL.md の「アクセシビリティは Issue 化しない」を見る。
サブエージェントにもこの除外を明示して渡し、報告に混ざってきたら Issue 化せず捨てる。

**ただし「既定設定のまま壊れている」ものは通常の UI バグとして拾う** — ここが線引き:

- 標準文字サイズのままテキストが切れる / 重なる → 拾う（Issue 化してよい）
- 文字サイズを上げると崩れる → 拾わない
- ボタンが実測 20pt 四方で誰にとっても押しにくい → 拾う
- 44pt にわずかに足りない（36pt 等）だけ → 拾わない
- 背景と同系色で標準設定でも文字が読めない → 拾う
- 実測 3.15:1 で AA 不合格、だが読める → 拾わない

## 体感品質

1. ハプティクスの一貫性（一部のボタンだけにあるのは不整合）
2. スケルトンローダー vs 全画面スピナー
3. 画面遷移の演出（アプリの世界観に対して素の Material/UIKit 遷移のままか）
4. キーボード回避（入力欄がキーボードに隠れないか、特にチャット/コメント系 UI）
5. SafeArea / ノッチ・ホームインジケータ対応（直値の padding で回避していないか）

## i18n・フォーマット

1. 文字列ハードコードの有無と l10n 基盤（arb / String Catalog）の有無
2. 日付フォーマットの実装方式が複数混在していないか（フォーマッタの一元化）

## ストア品質

1. アプリアイコン（形式・adaptive icon の前景余白）、スプラッシュ
2. ATT（トラッキング許可）・通知許可のリクエストタイミング（起動直後の連発は審査・体験の両面で悪い）
3. 権限拒否時のフォールバック UI（拒否したら機能が無言で死ぬ、が頻出バグ）
4. アプリ内レビュー導線の有無とタイミング
