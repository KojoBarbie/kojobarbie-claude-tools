# 提案Issueとsub-issueのフォーマット

## 提案Issue（1提案 = 1 Issue、ラベル: feature-proposal）

タイトル: `[カテゴリ/規模] 機能名` — 例の形式: `[新機能/M] ...`（カテゴリ: 新機能|改善|収益化、規模: S|M|L）

```markdown
## 概要

（何を作るか。2〜4文。ユーザーから見える変化を中心に）

## なぜ（根拠）

（以下のいずれか必須。**実物の引用**を含めること — 要約だけの根拠は不可）
- 競合レビュー: 「（レビュー原文の引用）」（アプリ名, ★n, 日付）が m 件系統
- コード観察: `path/to/file` に〜が既にあるため、〜が低コストで実現できる
- Analytics: 〜のファネルで（数値）が離脱している

## 前提

（この提案が成立するための前提。外れていたら見送るべき条件）

## 検証方法・成功指標

（リリース後に何をどう計測すれば成否が分かるか。Analytics接続済みなら計測イベント名まで。
未接続なら「レビュー・問い合わせで〜が観測される」など定性基準でよい）

## 子タスク分割ドラフト

（承認後にsub-issue化する分割案。この時点ではチェックリストの粗い箇条書きでよい）
- [ ] ...
- [ ] ...

---
👍リアクション or `go` ラベルで承認（sub-issueに分割されます）/ close で見送り（理由コメントをもらえると次回の提案が良くなります）
```

規模の目安: **S** = PR 1本で完結 / **M** = PR 2〜4本 / **L** = PR 5本以上の大型機能（Lはエピックとして親issue + 多めのsub-issueになる）。

## sub-issue（承認後に作成、1 sub-issue = 1 PR）

タイトル: 動詞で終わる実装単位（「〜を追加する」「〜を分離する」）

```markdown
## 目的

（親 #N のどの部分を実現するか。1〜2文）

## 変更内容

（何をどう変えるか。設計判断が必要な点は方針まで書く）

## 受け入れ条件

（実装したかどうかを後から客観的に判定できる、観測可能な形で）
- [ ] 〇〇すると△△が表示される
- [ ] ...

## 対象ファイルの見当

- `path/to/...`（新規 or 変更）

## 依存

（先に完了しているべきsub-issue番号。なければ「なし」）
```

書き上がりの基準: **ship-issueに番号を渡すだけで、追加の質問なしに実装が始められること**。
