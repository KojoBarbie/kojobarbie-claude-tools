# 判断ブロック（judge:v1）— PR を「判断書」として書くための規約

## なぜこの形式か

PR 本文は長らく「実装者が、なぜこの実装にしたかを説明する文書」として書かれてきた。
読者としてコードレビュアーを想定した書き方で、実測 3,000〜6,000 字になる。

しかしこの運用での実際の読者は **「マージしていいか決める人」1人だけ**で、
その人が知りたいのは「なぜこう書いたか」ではなく次の3つしかない。

1. 自分は何をすればいいのか
2. どのくらいのリスクがあるのか
3. 放置したらどうなるのか

判断ブロックはこの3つを本文の**先頭**に置き、従来の説明を `<details>` に畳む。
説明を消すわけではない（監査ログとしての価値は残す）。**読む順序を変えるだけ**。

## 全体テンプレート

```markdown
<!-- judge:v1
type: run
risk: low
cost: 5
expires: 2026-09-01
shots: DayMarks/132
-->

## 判断してほしいこと

**実機で「刻む」を3回タップして、カウントが増えることだけ確認してください。**
それ以外は読まなくて大丈夫です。

| | |
|---|---|
| 種類 | 動かす（約5分） |
| リスク | 低 — UI のみ。課金 / 権限 / データ移行には触れていません |
| 放置したら | 2026-09-01 に自動マージします |

<details><summary>実装の詳細（読まなくてよい）</summary>

（ここに従来の本文をそのまま入れる。実装計画・設計判断・テスト内容など）

</details>

Closes #120
```

HTML コメントに機械可読なメタを置くのは、GitHub 上の見た目を壊さずに
bash（`sed`/`awk`）からも Octokit からも同じものが読めるため。
`run_pr_expiry.sh` / `run_factory_reminder.sh` / pr-desk が全てこれをパースする。

**フィールドの順序と綴りは固定**（パーサが単純な行マッチで読むため）。値に改行を含めない。

---

## type — 人間に何を頼むのか

| 値 | 意味 | 既定 cost | 例 |
|---|---|---|---|
| `look` | スクショか変更の要約を見るだけ。手を動かさない | 0.2（10秒） | レイアウト変更・配色・空状態の見た目、ユーザー体験に影響しない計測/ドキュメント追加 |
| `run` | 実機で動かして確かめる | 5 | 通知・課金・ウィジェット・App Intents・Screen Time 拡張 |
| `decide` | 方針を決める。正解が技術的に定まらない | 10 | 価格、文言のトーン、機能を出すか引っ込めるか |
| `act` | **PR に付けない**（下記） | — | — |

### 決め方

1. 差分に UI ファイルが含まれ、**ビジュアルレビューでスクショが撮れている** → `look`
2. シミュレータでは再現しない副作用（通知の実配信・課金・システム拡張・ウィジェット更新）を含む → `run`
3. 技術的には正しいが、**どちらを選ぶかが好みや事業判断**である選択肢が残っている → `decide`
4. 上のどれでもなく、機械的な条件を全て満たしている → **そもそも auto-merge されるので判断ブロックは不要**

`decide` は安売りしない。「実装方針としてどちらが良いと思いますか」は `decide` ではない。
実装方針はセルフレビューと CI が担保する領域で、判断者に投げ返すべきものではない。

### `act` は PR ではなく issue にする

Firebase の権限付与、App Store Connect の設定、API キーの発行 — これらは
**PR のマージ可否とは無関係な人間タスク**であり、PR の形でキューに混ぜると
「10秒で終わるはずのキュー」に15分の作業が紛れ込んで、キュー全体が重く見える。

該当する場合は `human-task` ラベル付きの issue を切り、PR は draft のままそれを
`Blocked by #N` で参照する（詳細は `factory-build` SKILL.md のステップ2）。

---

## risk — 時効が来たときの既定動作を決める

| 値 | 定義 | 14日経過したら |
|---|---|---|
| `low` | センシティブ領域に一切触れず、CI green、ビジュアルレビュー済み | **自動マージ**（異議がなければ通す） |
| `mid` | 上記のどれかを満たさない。ただしセンシティブ領域ではない | 自動クローズ（元 issue は open のまま残るので再実装される） |
| `high` | センシティブ領域に1ファイルでも触れている | **時効なし**。人間が決めるまで残る |

**センシティブ領域**（`factory-build` 安全レール2 と同一の定義）:

- 課金 — StoreKit / RevenueCat / Product ID
- 権限 — `Info.plist` の Usage Description / entitlements
- データ移行 — `.xcdatamodel` / マイグレーションコード
- CI 設定 — `.github/workflows` / `ci_scripts`
- 署名設定

判定は `gh pr diff <n> --name-only` の結果に対して機械的に行う。迷ったら重い方に倒す。

---

## cost — キュー残高の単位

判断に**実際にかかる時間**を分で書く。既定値は type から引くが、実態に合わせて上書きしてよい
（例: スクショが8枚あって全部見る必要があるなら `look` でも `cost: 1`）。

この値の合計が **キュー残高**で、45分（`JUDGE_BUDGET_MINUTES`）に達すると
factory-build は新規着手を止める。**過少申告するとキューが実際より軽く見え、
人間が捌ける以上に PR が積まれる**ので、正直に書く。

---

## ask — 本文の一行目。ここが本体

「判断してほしいこと」の見出しの直下に、**太字1文**で書く。

### ルール

1. **動詞で始める**。人間が実行する具体的な操作を書く
2. **何がどうなっていれば OK かを必ず含める**。合格条件のない依頼は判断できない
3. **1文。2つ以上頼まない**。頼みたいことが2つあるなら PR を分けるか、重要な方1つに絞る
4. **コードを読ませない**。「この実装で良いか見てください」は禁止

4 が最も重要。実装の是非はセルフレビューと CI とテストが担保する領域で、
そこを人間に投げ返すと 4,000 字を読む作業に戻ってしまう。
人間に頼んでよいのは **機械が原理的に確認できないこと**（実機の挙動、見た目の良し悪し、事業判断）だけ。

### 例

| ❌ | ⭕ |
|---|---|
| 動作確認をお願いします | 実機で「刻む」を3回タップして、カウントが増えることを確認してください |
| レビューしてください | 添付のスクショで、オフラインバナーが一覧を隠していないことを見てください |
| この実装方針で良いか判断してください | 課金画面の価格を ¥480 と ¥600 のどちらにするか決めてください（根拠は詳細に記載） |
| 通知まわりを確認してください | 実機で通知を許可 → アプリを閉じて、翌朝8時に通知が1通だけ届くことを確認してください |

続けて「**それ以外は読まなくて大丈夫です**」を必ず添える。
これは礼儀ではなく仕様で、**読まなくてよい範囲を明示することが判断単価を下げる**。

---

## expires

PR 作成日 + 14日（`YYYY-MM-DD`）。`risk: high` の場合も書式上は入れるが、
時効ジョブは `high` を無視するので実質使われない。

pr-desk の「後で」ボタンはこの値を +7日する。

## shots

`$APP_FACTORY_HOME/screenshots/` からの相対パス（`{アプリ名}/{PR番号}`）。
ビジュアルレビューで撮った画像の置き場で、pr-desk がここを読んでカードに表示する。
撮れなかった場合はフィールドごと省略する（空文字にしない）。

---

## 旧本文の畳み方

既存の書き方（`## 概要` / `## 変更内容` / `## テスト` や factory-build の実装計画）は
**一字も削らずに** `<details>` の中へ移す。

```markdown
<details><summary>実装の詳細（読まなくてよい）</summary>

## 概要
...

</details>
```

`<details>` の中では見出しレベルをそのまま保ってよい（GitHub は正しく描画する）。
`Closes #N` は **`</details>` の外**に置く（畳まれた中にあっても機能はするが、
issue 連携を目視で確認できなくなるため）。
