# ビジュアル回帰レビュー — 実装した画面を実際に見る

コードレビューだけでは UI の品質は担保できない。**規範（design-concept）に書いてあることと、
画面に出ているものは別物**だからだ。この工程は「書かれた規範」ではなく「見た結果」で品質を測る。

> ここを省くと、モックやコンセプトシートをどれだけ良くしても完成品は良くならない。
> 実装が目標値に届いているかを誰も確認しないまま出荷されるため。

## 実行条件

差分に **UI ファイルが含まれるときだけ**行う。含まなければスキップしてよい（その旨は書かない）。

```bash
gh pr diff <pr> --name-only
```

UI ファイルの判定: `*View*.swift` / `*.tsx` / `*.jsx` / `*.dart` / `*.vue` /
アセットカタログ / スタイル定義ファイル。判断に迷ったら「含む」に倒す。

## Step 1: 画面を撮る

### iOS（XCUITest のスクリーンショット巡回テストがある場合 — 推奨）

`app-kickoff` が作る必須 issue に「スクリーンショット巡回テスト」があり、
主要画面を巡って `XCTAttachment` として保存するテストが用意されている。これがあれば一番確実:

```bash
xcodebuild test -scheme <Scheme> -destination 'platform=iOS Simulator,name=iPhone 16' \
  -resultBundlePath /tmp/rb_<pr>.xcresult -only-testing:<App>UITests/ScreenshotTests

# 添付画像を取り出す
xcrun xcresulttool export attachments \
  --path /tmp/rb_<pr>.xcresult --output-path /tmp/shots_<pr>
```

`review-ios-test-results` スキルがあれば、結果バンドルの読み解きはそちらに任せてよい。

### iOS（巡回テストが無い場合 — 起動直後の1枚だけ）

```bash
xcodebuild -scheme <Scheme> -destination 'platform=iOS Simulator,name=iPhone 16' \
  -derivedDataPath /tmp/dd_<pr> build
xcrun simctl boot "iPhone 16" 2>/dev/null || true
xcrun simctl install booted /tmp/dd_<pr>/Build/Products/Debug-iphonesimulator/<App>.app
xcrun simctl launch booted <bundle-id>
sleep 4
xcrun simctl io booted screenshot /tmp/shots_<pr>/launch.png
```

この場合、**撮れたのは起動直後の1枚だけ**であることをレビュー結果に必ず明記する。
そして「巡回テストを追加すると以後の全 PR で主要画面を見られる」と1行添える。

### Web / Flutter

プロジェクトの標準に合わせる（Playwright のスクリーンショット、`flutter test --update-goldens` 等）。
既存のテスト基盤があればそれに乗る。無いなら**この工程はスキップしてよい**
（スクショのためだけに新しいテスト基盤をこの PR で導入しない）。

### 撮れなかったとき

**黙って飛ばさない。** ビルド失敗・シミュレータ不在・テスト不足など理由を書いて
「ビジュアル未確認」と PR に残す。省略が「確認済み」に見えるのが一番まずい。

## Step 2: 見てレビューする

撮った画像を **Read ツールで実際に見る**（パスを眺めるだけでは意味がない）。
そのうえで `app-design-craft` の9レンズで点検する。ただし**全レンズを均等に見ない** — この PR で
変わった画面に効く軸に絞る。

### 突き合わせる基準（この順で）

1. **`docs/design-concept.html` との差分** — 配色・余白スケール・角丸・強調装置・ボイスが
   コンセプトシート通りか。ズレていれば「実装がコンセプトから逸脱」として指摘する
2. **紙芝居モック（showcase）との差分** — 画面構成・遷移・演出がモックに届いているか。
   **モックにあって実装に無いものは、原則すべて指摘対象**（モックは目標値であって願望ではない）
3. **状態の網羅（レンズ8）** — 空状態・読込中・エラーが実装されているか。
   スクショが正常系1枚しかない場合は、**コードを読んで**この3つの有無を確認する
4. **参照リファレンスと並べて見劣りしないか** — `$PRD_VAULT_DIR/design-vault/` があれば
   同じ画面種別（`screen`）のカードを引き、並べて見る。
   「他社の同種画面と比べて何が足りないか」は最も具体的な指摘になる

### 指摘の書き方

- **「なぜユーザーが困るか」で書く**。「余白が狭い」ではなく
  「行間が詰まっていて一覧を流し読みできない。1件あたりの高さを 56→72 に」
- **重箱の隅をつつかない。** 世界観に効く3点までに絞る
- 良い点も1つは書く（何が効いているかを言語化しておくと次に再現できる）

## Step 3: PR に残す

所見を PR コメントとして投稿する。**コメントは `🤖 ビジュアルレビュー:` で始める**。

```markdown
🤖 ビジュアルレビュー: <対象画面>

**確認方法**: XCUITest 巡回（3画面） / スクショ: `/tmp/shots_123/`
（または「起動直後1枚のみ」「未確認（理由）」）

**良い点**
- ...

**指摘**
1. **<結論1行>** — なぜ問題か → どう直すか（数値で）
2. ...

**未確認**
- レンズ7（動き）はスクショでは判定不可。コード上は遷移アニメーションの指定なし
```

画像そのものは PR に添付しない（GitHub の添付は Web UI 専用で API から貼れない）。
代わりに**ローカルの保存先パスを書く**。人間が見たいときに開ける。

## Step 4: 指摘への対応

通常のレビュー指摘と同じ往復に合流させる（`ship-issue` のステップ6 / `factory-build` の修正フェーズ）。
**1往復で止める**ルールも同じ。残った指摘は PR に残して人間の動作確認に委ねる。

## やらないこと

- スクリーンショットをリポジトリにコミットしない（PR ごとに増えて肥大する）
- スクショを撮るためだけに新しいテスト基盤を導入しない（別 issue にする）
- ピクセル単位の比較（スナップショットテスト）はしない。ここで見たいのは**設計判断**であって差分検知ではない
