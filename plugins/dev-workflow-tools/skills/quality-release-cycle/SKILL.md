# quality-release-cycle

アプリの品質を「監査 → Issue 化 → 実装 → リリース」のサイクルで維持するためのスキル。
実装フェーズは `ship-issue` スキルに委譲し、このスキルは**入口（監査）と出口（リリース）**を担当する。

このスキルの価値の中心は、監査そのものよりも**規律**にある:

1. サブエージェントの報告を鵜呑みにせず、「高」判定は必ずコードで裏取りする
2. open + closed の既存 Issue と照合してから Issue 化する（修正済みの再発見・追跡中の重複を防ぐ）
3. 「既に良い実装」も記録する（次回監査と実装者の無駄な作り直しを防ぐ）
4. リリース可否は ✅/⚠️/❌ の三択で機械的に出す

## ステップ 0: リポジトリ固有情報の読み込みとスタック検出

まず対象リポジトリの `.claude/quality-cycle.md` を探して読む。これは以下を記すリポジトリ固有の設定ファイル:

- テストコマンド（例: `fvm flutter test`、`xcodebuild test -scheme App`）
- リリースフロー（TestFlight / Play への配信経路、手動デプロイが必要なもの）
- トラッキング Issue の番号
- 対応済み監査の履歴（「PERF-1〜6 は修正済み」等 — 再発見防止のため）

**ファイルがなければ**: CLAUDE.md・README から同じ情報を拾い、以下で不足を自動検出する。監査/リリース判定の完了後に、
判明した内容で `.claude/quality-cycle.md` の生成を提案する（次回以降の検出コストをなくすため。勝手にコミットはしない）。

スタック検出（該当ファイルの存在で判断）:

| 検出物 | 判定 | 使う参照ファイル |
|---|---|---|
| `pubspec.yaml` | Flutter | `references/audit-flutter.md` |
| `.fvmrc` / `fvm_config.json` | Flutter コマンドは `fvm flutter` 経由 | 同上 |
| `*.xcodeproj` / `Package.swift` | iOS ネイティブ（Swift/SwiftUI） | `references/audit-ios.md` |
| `firebase.json` / `functions/` | Firebase バックエンド | `references/audit-backend.md` |
| `supabase/` / サーバーディレクトリ / API クライアント層 | その他バックエンド | 同上（汎用セクション） |
| `.github/workflows/` | CI あり | `references/audit-quality-infra.md` |

UI/UX とストア観点はスタックによらず `references/audit-mobile-common.md` を使う。

## モード判定

| モード | トリガー例 | やること |
|---|---|---|
| `audit` | 「監査して」「品質チェック」「UI/UXの状態を見て」 | 監査 → 裏取り → Issue 化 |
| `release` | 「リリース準備」「リリースできる状態？」 | リリース可否判定 → 段取り提示 |
| `status`（引数なし） | 「品質サイクルの状況は？」 | 現状把握 → 次アクション推奨 |

`--dry-run` 指定時（または「Issue化はせずに」等の指示時）は Issue 作成を行わずレポートのみ出力する。

## audit モード

### 1. スコープを決める

- 引数でスコープ指定があればそれに従う（例: 「設定画面だけ」「バックエンドだけ」）
- 指定がなければ**前回監査以降の差分**を中心に全体を見る:
  - トラッキング Issue（`gh issue list --search "[Tracking]" --state all`）の作成日を起点に
    `git log --oneline --since=<日付>` で変更の集中している領域を重点対象にする
  - 初回または半年以上空いていればフル監査

### 2. 監査を実行する

検出したスタックに対応する references/ の監査観点を読み、**実行形態はスコープの広さで選ぶ**:

- **フル監査**（アプリ全体）: 4次元（パフォーマンス / UI/UX / バックエンド / テスト・CI）を
  **読み取り専用サブエージェント（Explore 等）で1メッセージ内に並列起動**する。各調査は独立なので並列で待ち時間が1本分になる
- **スコープ監査**（1画面・1モジュール程度）: サブエージェントを展開せず**自分で直接調査する**。
  小スコープでの並列展開は起動・統合のオーバーヘッドの方が大きい（実測でベースラインの3倍以上の時間がかかった実績あり）

各サブエージェントのプロンプトに必ず入れるもの:

- リポジトリの絶対パスと対象スコープ
- 「発見ごとに severity（高/中/低）・file:line・問題・1行の修正案」という報告形式
- 「既に良い実装（GOOD）も列挙する」という指示
- 事前に取得した既存 open Issue 一覧（`gh issue list --state open --limit 100 --json number,title`）と
  「重複する指摘は Issue 番号を添えて重複と明記」する指示
- 「一般論ではなくこのコードベースに根拠のある指摘だけを返す」という縛り

### 3. 「高」判定の発見はコードで裏取りする

サブエージェントの報告は**そのまま信じない**。もっともらしいが誤り・過大な指摘が混ざる（「毎フレーム再ビルド」が
実際は最大20回だった、という訂正実績あり）。severity「高」は自分で Grep / Read して事実確認し、
裏取りできなければ Issue 化せずレポートに「未確認」として残す。
「定義されているが呼ばれていない関数」（配線漏れ）は grep で呼び出し元まで確認する — この観点で通知機能の未配線を発見した実績がある。

### 4. 既存 Issue と照合する

open だけでなく **closed も**照合する（修正済みの再発見を防ぐ）:

```bash
gh issue list --state all --limit 200 --json number,title,state
```

- 完全重複 → Issue 化しない（レポートに「#NN で対応済み/追跡中」と記す）
- 部分重複 → 既存 Issue を参照する形で差分だけ Issue 化
- リポジトリに仕様ディレクトリ（`.kiro/specs/` 等）があれば、既に計画済みの機能は Issue 本文でそこを参照する

### 5. Issue を作成する

`references/issue-format.md` のテンプレートに従う。要点:

- 本文はテンポラリファイルに書いて `gh issue create --body-file` で投稿（エスケープ事故防止）
- 1 Issue = 1 まとまりの作業。小粒の指摘は「小規模クリーンアップまとめ」として1本に束ねる
- 実害のあるもの（配線漏れ・リーク等）は `bug`、改善は `enhancement`、文書は `documentation`

**1回の監査で新規起票する Issue は最大 10 件まで**。裏取り済みの発見が10件を超える場合は、
severity（高 → 中 → 低）と実害の大きさで並べ替え、上位10件だけを起票する。
束ね（小粒指摘の「まとめ」1本化）を先に行ってから10件に収めること。
溢れた分は起票せず、最終レポートとトラッキング Issue のコメントに「今回未起票（次回候補）」として
一覧で残す（次回監査で再発見・再検討できるように）。この上限は Issue 一覧が一度に大量流入して
埋もれるのを防ぐためのもので、発見の握りつぶしではない。

### 6. トラッキング Issue を更新する

- 既存の「[Tracking]」Issue があれば、新規 Issue を優先度別にコメントで追記する
- フル監査で発見が多い場合は新しいトラッキング Issue を作り、古い方と相互リンクする
- 推奨着手順の基本形: **効果の大きいバグ修正 → リリース基盤（デプロイ CI・runbook）→ 計測基盤 →
  パフォーマンス → UI/UX 基盤 → UI/UX 応用**。依存関係を明記する
  （例: デザイントークン統一はダークモードの前提、計測基盤はパフォーマンス改善の効果検証の前提）

### 7. 最終レポート

必ず含める: 起票した Issue 番号と1行説明（優先度順）、Issue 化しなかった発見とその理由（重複/裏取り不能/軽微）、
「既に良い」と確認できた実装。

## release モード

`references/release-checklist.md` を読み、チェックリストを上から実行して判定する。

- 確認はすべて読み取り操作なので自由に進めてよいが、**タグ作成・リリース作成・デプロイ・バージョン変更は
  ユーザーの明示的な指示を得てから**
- 判定は「✅ リリース可 / ⚠️ 条件付き可（残作業リスト） / ❌ 不可（ブロッカー）」の三択で明示する
- ブロッカーの解消は `ship-issue <番号>` を提案する

## status モード

1. トラッキング Issue の残 Issue 数（優先度別）を集計
2. 前回監査からの経過日数と、その間のマージ済み PR 数を確認
3. 次のアクションを**1つだけ**推奨する: 「高」が残っていれば `ship-issue <番号>`、
   残っていなければ `release`、監査が1ヶ月以上古く変更が多ければ `audit`

## 定期運用

ユーザーに提案してよい運用例（勝手にスケジュールは作らない）:

- 週次: `status`（残 Issue と次アクションの確認）
- リリース前: `release`
- 月次 or 大きな機能マージ後: `audit`(差分スコープ)
