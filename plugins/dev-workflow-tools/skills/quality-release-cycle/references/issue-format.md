# Issue 作成フォーマット

## タイトル

`[カテゴリ] 一文で問題がわかるタイトル`

カテゴリ: `PERF` / `UI/UX` / `Backend` / `CI` / `Test` / `Monitoring` / `Release` / `Docs`

良い例: `[PERF] ウォームアップが実チャットと別のサービスを叩いておりコールドスタート対策が無効化されている疑い`
悪い例: `パフォーマンス改善`（何をするのか不明）

## 本文テンプレート

```markdown
## 問題

<何が起きているか。**必ず file:line の根拠を添える**。裏取りした事実と推測は区別して書く>

## 対応案

1. <具体的な修正手順。番号付き>
2. <あれば代替案>

## 関連

<関連 Issue（#NN）、仕様ディレクトリ、依存関係（「#NN を先にやると効率が良い」等）。なければ省略>

## 優先度

**高/中/低** — <なぜその優先度か1行>

---
📋 <日付> 実施の監査より
```

## ラベルの使い分け

- `bug`: 意図と実装が食い違っているもの（配線漏れ、URL 不一致、リスナーリーク等）
- `enhancement`: 改善・新規対応
- `documentation`: 文書の整備・整合

リポジトリに独自ラベル体系があれば（`gh label list` で確認）そちらを優先する。

## 作成コマンド

本文は必ずファイル経由で渡す（インライン文字列はエスケープ事故のもと）:

```bash
cat > /tmp/issue_body.md <<'EOF'
<本文>
EOF
gh issue create --title "<タイトル>" --label "<ラベル>" --body-file /tmp/issue_body.md
```

## トラッキング Issue

フル監査後は優先度マトリクスをまとめたトラッキング Issue を作る。構成:

1. 🔴 優先度: 高 — Issue 番号・内容・効果の表
2. 🟡 優先度: 中 — カテゴリ別に列挙
3. 🟢 優先度: 低
4. 推奨着手順 — 依存関係込みで（バグ修正 → リリース基盤 → 計測基盤 → パフォーマンス → UI/UX 基盤 → 応用）
5. 「既に良い」実装の一覧 — **変更不要と明記**（無駄な作り直しの防止）
