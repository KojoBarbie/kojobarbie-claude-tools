# リリース準備チェックリスト

上から順に確認し、結果を ✅/⚠️/❌ で記録する。確認はすべて読み取り操作なので自由に進めてよいが、
**タグ作成・リリース作成・デプロイ・バージョン変更は必ずユーザーの明示的な指示を得てから**行う。
リポジトリ固有のリリースフロー（配信経路・手動デプロイの有無）は `.claude/quality-cycle.md` を優先する。

## 1. コードの健全性

```bash
git status                      # 作業ツリーがクリーンか
gh pr list --state open        # マージ待ち PR（リリースに含めるべきものが残っていないか＝スコープ判断）
gh run list --branch <デフォルトブランチ> --limit 5   # CI が green か
gh workflow list --all         # disabled_manually な workflow がないか（配信系が無効化されたまま、の実例あり）
```

- テストはリポジトリ固有のコマンド（`.claude/quality-cycle.md` 参照）。CI が green なら省略可
- サーバーコードに変更が含まれる場合はサーバー側の test + lint も確認

## 2. ブロッカー Issue の確認

```bash
gh issue list --label bug --state open
```

- トラッキング Issue の 🔴（高）に**ユーザー影響のあるバグ**が残っていないか
- 残っていても即 ❌ にせず「⚠️ 条件付き可」として、リリースに含めるか次回に回すかの判断材料
  （工数・影響範囲・サーバー側だけで直せるか）を添えて提示する

## 3. バージョン

- 現在のバージョンを確認（Flutter: `pubspec.yaml` の `version:`、iOS: プロジェクト設定 / xcconfig）
- 前回リリース以降の変更内容から semver を判断: **機能追加が含まれるなら minor**、修正のみなら patch。
  「patch のまま新機能入りでリリース」は避ける
- CI がビルド番号を自動採番している場合（epoch 秒等）はローカルのビルド番号が参考値であることを明記

## 4. リリース内容の整理

```bash
git log <前回リリースタグ>..HEAD --oneline
```

- ユーザー向け変更点（What's New 案）をまとめる
- **アプリ側の新機能がデプロイ済みバックエンドを前提にしていないか**確認する
  （例: 新しい集計表示は、サーバー側の集計処理が先にデプロイされている必要がある）
- バックエンド変更が含まれる場合はデプロイ順序を明示:
  1. 後方互換なサーバー変更 → アプリ審査前に先行デプロイ
  2. 新クライアント必須の変更 → 審査通過後にデプロイ（**旧クライアントが壊れないか必ず検討**）
- DB ルール・インデックス等の付随デプロイ（Firebase なら `firebase deploy --only firestore`）も忘れない

## 5. 配信フロー

リポジトリの CI 定義（`.github/workflows/` 等）から実際の配信経路を確認して段取りに落とす:

- タグ / Release publish で何が発火するか（TestFlight 配信、ストア提出、App Distribution）
- 手動ステップ（Play Console 提出、審査情報更新）はどれか
- 段階的公開（phased release / staged rollout）を使うか

## 6. 判定の出し方

最後に必ず三択で明示する:

- ✅ **リリース可** — 次の一手（バージョン bump PR → Release 作成）を提示
- ⚠️ **条件付き可** — 残作業リストと、それを飛ばした場合のリスクを添える
- ❌ **不可** — ブロッカーと解消手順（`ship-issue <番号>` の提案）を添える
