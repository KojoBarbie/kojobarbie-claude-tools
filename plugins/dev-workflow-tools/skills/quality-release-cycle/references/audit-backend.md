# 監査観点: バックエンド

Firebase（Cloud Functions + Firestore）を主対象に書いてあるが、「汎用」節の観点は
Supabase / 自前 API サーバーでも同じように適用する。

## インベントリ（まず全体像を表にする）

関数/エンドポイントごとに: トリガー種別・リージョン・memory/timeout・minInstances・retry 設定。
コメントと実体の乖離（「index に書いてあるがファイルが存在しない」等）もここで拾う。

## 汎用: 配線漏れ（最重要観点）

**「定義されているが呼ばれていない」機能を grep で洗い出す。** export された関数・通知送信・イベント発火について
呼び出し元を検索し、ゼロ件のものは配線漏れの疑いとして裏取りする。
「レターは保存されるが通知が飛ばない」型のバグはテストでも UI でも見えにくく、この観点でしか見つからない実績がある。

## 汎用: レイテンシ

1. ユーザー体感に直結する経路（チャット応答等）の直列 await — 並行化・キャッシュできる読み込みが直列になっていないか
2. ストリーミング対応（LLM 応答をバッファせず流しているか）
3. コールドスタート対策の実効性 — **ウォームアップ先と実エンドポイントが同一サービスか**を URL レベルで確認
   （関数ごとに別サービスになるため、別関数を温めても無意味。実際に不一致が見つかった実績あり）

## 汎用: コスト・スケーラビリティ

1. スケジュールバッチの全ユーザースキャン（ユーザー数に比例する read）を避ける設計になっているか
2. `limit` なしの collection 全件取得 + メモリ展開（ユーザー増で timeout/OOM になる時限問題）
3. バッチ内のユーザー直列 await（並列チャンク処理との混在は統一する）
4. LLM API の max_tokens・モデル選択がタスクに対して過大でないか
5. 認証必須エンドポイントの **App Check / レート制限**（正規トークンだけで課金 API を直叩きできる構造は濫用コストの入口）

## 汎用: 信頼性

1. スケジュールジョブの**冪等性**（再実行しても二重生成・二重送信しないか）
2. ユーザー単位の部分失敗分離（1人の失敗が全体を止めない try/catch + エラー集約）
3. リトライの分類（リトライ可能/不可能エラーの判別、指数バックオフ、無効トークンの削除）
4. タイムゾーン処理の一貫性（手動 offset 計算と TZ ライブラリの混在）
5. 外部ストレージ読み込みの障害時挙動（一時障害を「空データ」と誤認して上書き消失しないか）

## Firebase 固有

1. `firestore.rules` / `storage.rules`: ユーザーデータ隔離（本人のみ read/write）、サーバー専用コレクションの
   クライアント書込禁止、フィールド単位の更新制限（`diff().affectedKeys()`）
2. `firestore.indexes.json` とクエリの整合
3. シークレットが Secret Manager / defineSecret 管理か（コード・env ファイルへのハードコードがないか、.gitignore）
4. functions の Node ランタイムと SDK のバージョン（サポート期限）

## プロンプト・LLM 統合（該当時）

1. ユーザー入力（名前等）がプロンプトに入る箇所のサニタイズ choke point
2. プロンプトキャッシュの実効性（最小トークン数に届いているか — silent ignore に注意）
3. 構造化出力のパースがストリーム跨ぎでも壊れないか
